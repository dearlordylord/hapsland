# Authenticated port IPC prototype

**Purpose:** Record the production-code experiment replacing resident Unix sockets with loopback ports and evaluating ScriptC independently.
**Status:** Archived prototype on `prototype/port-ipc`. The owner chose to retain Bun and the existing Unix-socket production transport; this branch preserves the experiment for reference.
**Authority:** Implementation and validation evidence, with advisory recommendations; this report does not extend the accepted platform support declaration.
**Expected use:** Consult the experiment and its limitations when reconsidering compiler or transport alternatives; this branch is not a production adoption proposal.
**Lifecycle:** Branch-scoped experiment evidence. Keep this report with the archived prototype and review it if the experiment is resumed. Before any future production merge, consolidate adopted decisions into architecture and testing guidance, update inbound links, and delete this report. The existing production transport remains unchanged outside this branch.

## Implementation

The worktree branch `prototype/port-ipc` replaces the resident and inspection transports in production code. Application framing remains version one. Each server binds an ephemeral port on `127.0.0.1`; a private endpoint record publishes its port, certificate, authentication token, PID and lifetime. The certificate's private key remains in resident memory. TLS verifies the server before the client sends the token; an acknowledgement precedes application data. Ports and tokens are independent for the 32-slot hook endpoint and four-slot inspection endpoint. Existing ownership locks, lifetime fencing, request bounds and cancellation remain in their owning modules.

`@peculiar/x509` 2.1.0 and `reflect-metadata` 0.2.2 are bundled build dependencies (**DEPEND ON** for this prototype). Certificate generation is lazy and resident-only. The resident entry point initializes reflection before Bun evaluates that lazy module; a compiled probe exposed an ordering failure without that initialization. This adds no OpenSSL executable requirement for users. The security model trusts the current OS user and its private files; TCP does not provide Unix peer credentials. It does not protect against a malicious process already able to read those private files.

## Measurements

The [paired declaration](../evidence/package/port-ipc-paired-declaration-04.json) and [results](../evidence/package/port-ipc-paired-04.json) identify the runner and executable hashes. Both variants use installed-layout Bun standalone executables. The port candidate is extracted from the fresh archive used by the passing package boundary gate, and its CLI/resident bytes match those built for that archive. The Unix baseline was built before transport changes; it is an experimental comparator, not a retained production fallback. The same final runner measured both variants, alternating variants and runtimes for ready-resident calls. All 108 hook invocations completed successfully: 15 ready-resident and three cold-resident calls for each of Pi, Claude Code and Codex CLI per variant. Pi returned `registered`; Claude Code and Codex CLI completed their intentionally quiet before-edit path. The benchmark verifies exits, deadlines and resident readiness, and does not independently inspect Claude/Codex permit state. Separate installed-hook tests establish admission and delivery behavior. These are CLI hook envelopes, not real agent sessions or source-edit/reviewer latency measurements.

| Hook | Unix ready median | Port ready median | Unix cold median | Port cold median |
| --- | ---: | ---: | ---: | ---: |
| Pi | 100.55 ms | 113.63 ms | 215.87 ms | 232.60 ms |
| Claude Code | 98.23 ms | 105.94 ms | 212.73 ms | 217.71 ms |
| Codex CLI | 97.59 ms | 106.60 ms | 212.00 ms | 227.34 ms |

This Linux arm64 offline sample has uncontrolled scheduling and file caches. Three cold samples cannot establish a population percentile. It shows a modest local latency cost for authenticated ports and no measured startup improvement. Earlier baseline attempts and the failed first paired run remain separate records; the first paired run failed before measurements because the compiled certificate module required eager reflection initialization.

## ScriptC result

The [initial evaluation](../evidence/package/scriptc-port-evaluation.json) tested the existing full CLI and raw port client with published ScriptC 0.2.4. A [minimal TCP probe](../scripts/scriptc-tcp-probe.ts) compiled and echoed successfully. A [production port probe](../scripts/scriptc-resident-port-probe.ts) failed on `Socket.removeListener` and `destroy(error)`. The full CLI build failed on `node:readline/promises`; CLI coverage failed with an internal lowerer error. These results establish only those entry points and compiler configurations; the full CLI result does not decide compatibility of the intended standalone hook executable or static Effect support. The standalone hook evaluation below supplies that narrower evidence. Existing [research](https://github.com/dearlordylord/hapsland-research/blob/master/PRODUCT-RESEARCH-ADVISORY-2026-10-06-SCRIPTC.md) remains advisory.

The subsequent [local compiler fix and evidence](../evidence/package/scriptc-coverage-local-fix.json) diagnose the coverage crash as property dispatch that ignored an island-backed value behind a native union declaration. The [source patch](../evidence/package/scriptc-coverage-local-fix.patch) fixes optional-chain receiver dispatch and island-backed union property reads. Six regression tests and ten selected existing coverage tests passed; compiler typechecking and owned-file lint/format checks passed. The patched source CLI completed coverage with exit zero. This is a local, focused compiler fix, with no upstream PR, publication or full native compiler qualification. Published ScriptC 0.2.4 remains unchanged, and the other compilation blockers remain. The setup-interaction prototype was also checked and failed compilation on stream types and Effect generator/callback boundaries. These observations concern the tested entry points: an isolated future HTTP hook executable needs its own compilation and behavioral evaluation before deciding ScriptC's suitability for that executable.

## Standalone hook evaluation with static Effect

The [follow-up evaluation](../evidence/package/scriptc-hook-static-evaluation.json) freezes the intended standalone `src/hook-main.ts` implementation at commit `ee3b80999cd8710fd9d473f371d745bd2231fc51` inside this worktree's ignored evaluation directory. It applies the port transport to that copy and replaces the Bun-specific clock import with a native machine-monotonic adapter. Administration and interactive setup are outside this entry point. The candidate passes TypeScript checking. Other worktree files and the production hook commands were not changed by this evaluation.

The published native ScriptC CLI 0.2.4 failed with an internal `SC3004` error even on a small Effect control. The matching published Node-hosted `@scriptc/compiler` 0.2.4, LLVM helper and runtime packages successfully built native Effect and Effect/Schema controls using `--npm-static effect`. Their valid output matched Bun; the schema executable rejected incorrect types, null and malformed JSON. This demonstrates the tested Effect capability, not complete compatibility. Node is a build-host dependency for this route, not a dependency of those native executables.

The intended hook graph was then compiled with the upstream static package selection (`effect`, `@effect/platform-node`, `@effect/platform-node-shared`, `undici`), both without and with the dynamic engine. Both attempts failed. Remaining diagnostics include filesystem ownership and bigint-stat APIs, generic/union and callback-container shapes, and the raw transport's socket calls. Diagnostic counts include cascades and must not be treated as independent defects. These results concern the standalone hook graph, rather than the full administration CLI.

An [isolated HTTPS control](../scripts/scriptc-https-probe.ts) checks whether replacing raw socket calls helps. Its `minVersion` option is unsupported by this compiler. A derived control omitting only that option compiles, but the trusted handshake fails before application data with the existing P-256 certificate, with TLS 1.2-only and TLS 1.3-only servers, and with an RSA-2048/TLS 1.2 fixture. The cause remains unresolved; negative authorization/certificate outcomes are inconclusive while the positive path fails. The [same fixture runner](../scripts/check-scriptc-https.mjs) with Bun passes valid requests, wrong certificate, wrong token, split UTF-8, stalled response and oversized response checks. The production TLS policy remains unchanged.

The recommendation is to retain Bun for the current hook implementation (**REJECT** ScriptC as a drop-in compiler for the tested graph), **BORROW** the upstream static Effect configuration, and keep the Node-hosted compiler as an **OPTIONAL INTEGRATION** for a future compiler-compatible hook. No runnable production ScriptC hook was produced, so no end-to-end hook performance improvement is claimed. Linux arm64 is the only executed target. The [build runner](../scripts/evaluate-scriptc-hook.mjs), retained input hashes and per-experiment records identify the evaluated inputs; no upstream PR or production rollout occurred.

## Verification boundary

Executed focused checks cover private endpoint validation, TLS/token rejection, stalled and trickled authentication, version-one request framing, response delivery, inspection/control isolation, import boundaries and source resident lifecycle. The compiled resident idle-retirement check passed after the reflection ordering fix. A final client test reproduced corruption when a Unicode character crossed TLS response chunks; the client now uses a streaming UTF-8 decoder, matching the server framing boundary. Typechecking, generated configuration checks and changed-file lint passed. The final fresh-package boundary gate passed all 111 selected cases in eight files, including the packaged split-Unicode response check, covering Claude delivery, Pi installed extension delivery and fault recovery, resident process lifetime, CLI contracts and onboarding dispatch. Both Linux and macOS arm64 binaries were built; only Linux execution was exercised. The [validation inventory](../evidence/package/port-ipc-validation.json) records each selected run, source/archive identity and numbered objective. No full-project coverage gate was run; these are focused checks for the affected transport, process and package boundaries.

The transport does not establish Windows, x64, or new macOS execution support. Native parsing, credential storage and the machine clock remain existing platform constraints. No external Jev requests or authenticated native agent sessions are needed for these offline checks. The owner decision is to retain Bun and Unix sockets in production. Authenticated ports remain an archived experiment on this branch; the evidence does not justify production adoption.

## Dependency decision gates

The in-process certificate generator and reflection polyfill are conditional **DEPEND ON** recommendations for this prototype, not unconditional production adoption. Source class is package source/metadata; the compiled and source fixtures above provide separately identified runtime evidence. The following gates are mandatory for adoption across the existing declared targets.

| Gate | Evidence and status | Remaining condition or resolution |
| --- | --- | --- |
| License compatibility | **PASS** for the prototype: both pinned packages declare MIT licenses; existing bundled distribution permits MIT components. | Retain the redistribution notices with distribution. |
| API and versioning | **PASS** for the exact pins: self-signed P-256 generation and PEM export passed source and compiled checks. | Pin upgrades and rerun certificate/transport checks; no guarantee for untested releases. |
| Required host/workflow conformance | **UNRESOLVED** across all declared targets: Linux source/installed checks passed, both arm64 targets built. | Run the same installed hook and authentication cases on macOS before extending execution claims. Native agent sessions remain a separate support gate. |
| Trust, egress, credentials and supply chain | **PASS** for the tested local boundary: generated keys stay in memory; private records publish only certificate/token; wrong certificates/tokens and unsafe files are rejected. Generation performs no external requests. | Compatibility ownership includes reviewing pinned transitive changes; current-user compromise remains outside this boundary. |
| Failure and deadline behavior | **PASS** on Linux: failed compiled initialization was diagnosed and fixed; unsafe endpoints, trickled authentication, hook timeout/crash and resident replacement checks passed. | Repeat platform-specific failure cases on macOS. |
| Maintenance and compatibility ownership | **UNRESOLVED** for production adoption: dependencies are exactly pinned; release/source metadata alone does not establish a support commitment. | Transport owner must accept responsibility for pin review and both-target checks when adopting this branch. |
| Integration and adapter cost | **PASS** for the bounded prototype: native TLS, a bounded record, token handshake and one lazy certificate module replace the Unix transport; no new user runtime or executable is required. | Accept the measured latency cost explicitly when deciding adoption. |
| Replacement and exit | **PASS** for the prototype: discard this isolated worktree to retain the original Unix implementation; the certificate generator is confined to one resident module. | Production replacement requires a new reviewed certificate implementation; there is no parallel legacy transport in this branch. |
