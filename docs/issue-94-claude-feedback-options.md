# Issue #94: Claude finding feedback options

**Decision status, 2026-09-24:** proposal for product-owner review. This document selects a next **offline** experiment, not a Claude support claim, an authenticated host run, or a change to Hapsland's current advisory policy. It concerns the existing Noul-only, successful direct `Edit`/`Write` path. It introduces no type/function review branch, new rule set.

## What is being reviewed

The question is how Hapsland should word and deliver a **current, acting rule finding after a completed Claude edit**, so Claude has a clear repair opportunity. The question is not whether Jev review ran: the approved authenticated Stage A finding arm had one matched native edit, successful hook, `completed-findings` outcome, and one classified rule-finding submission, but no distinct later native repair. The control passed. Thus the [Stage A record](issue-94-host-validation.md) proves submission without observed repair; it does not prove that the model read, ignored, or could not act on the finding.

The subsequent [offline delivery fixture](issue-94-delivery-diagnosis.md) used exact Claude Code `2.1.218`, the compiled Hapsland CLI and controlled review, and a scripted local provider. Its second provider request contained the **production** finding text through `hookSpecificOutput.additionalContext`. A top-level `{ "decision": "block", "reason": "..." }` envelope also reached the second request, but its rule reference was authored by the fixture wrapper, not production Hapsland. Plain stdout did not reach that request. These are provider-request inclusion observations, not real-model interpretation or repair. They weaken a universal “context is undeliverable” explanation of Stage A, but do not identify its cause.

The [#97 delivery baseline](issue-97-delivery.md) concerns Codex `0.156.1` and Luna, not Claude. It shows that a finding ready at a later hook or bounded Stop can produce a same-turn repair in selected synthetic sessions, while a late finding can miss a headless session. Its Stop clock and IPC results cannot be transferred as a Claude latency or policy guarantee. Claude already has a synchronous PostToolUse handoff with a 3,900 ms CLI deadline, 4,400 ms bridge ceiling, and five-second native limit; the [ticketed terminal collection work](issue-94-terminal-collection-proposal.md) fixes the selected offline all-clear polling failure within those bounds. The feedback options below retain those ceilings.

Claude's [hook documentation](https://code.claude.com/docs/en/hooks#posttooluse-decision-control) describes PostToolUse block reasons as prompts after the tool has executed; that documentation does not prove behavior in the pinned host.

## Options

| Option | Host behavior and product meaning | Latency and cost | Notice, clear, stale, and unavailable outcomes |
| --- | --- | --- | --- |
| **A. Keep `additionalContext`; request repair explicitly (recommended offline candidate)** | For a validated current Noul finding, retain the advisory PostToolUse envelope and its rule ID, declaration/path, probability, and configured advice text. Add a short instruction such as “Please repair this finding in the file you just edited, then continue.” The edit remains complete; Claude may choose whether and how to repair. This is a wording change to existing advice, not a new enforcement mode. | No extra review call or hook stage. Payload grows modestly within the existing five-item/2 KiB handoff cap; the synchronous wait stays under the existing deadlines. More forceful wording may increase model turns and repair attempts, but that effect is unmeasured. | A current finding may request repair. An operational notice remains a notice and never asks for repair. `clear`/`no-work` remain quiet. Stale or unavailable results never request repair; a policy-permitted operational notice may still be delivered under the existing cooldown. Revalidate before handoff as today. |
| **B. Use top-level PostToolUse `decision: "block"` for acting findings** | Emit a bounded `reason` containing the current finding and explicit repair request after the successful edit. Claude documentation calls this a block decision, but it does not roll back the edit. This changes Hapsland's present advisory contract to a host-directed repair signal. Hapsland would define its own threshold and authority using its existing validated Noul findings. A separate Stop policy could later catch missed or late findings, but is **not included** in this option's initial experiment. | Same review path and synchronous deadline if used at PostToolUse; no evidence yet that real Claude repairs more often. A Stop path would add hook invocation, recipient/revalidation logic, bounded waiting, and possible extra model turns, so it needs its own specification and latency budget. False positives would have stronger workflow consequences than in A. | Block **only** when at least one current acting rule finding is selected. Never block for notice-only, clear, no-work, stale, timeout, credential/backend failure, or unknown status. A notice may accompany a finding only if the bounded output and policy already permit it; it must never be the reason for a block. Expired/superseded findings are suppressed before serialization. A future Stop path must prevent repeated blocks and stale replay, with explicit limits. |
| **C. Defer Claude feedback change** | Keep the current advisory text and `additionalContext` behavior. Do not claim support from Stage A. Resolve the reaction question through further read-only or offline evidence before changing policy. | Zero implementation latency or semantic cost now; a current finding can still be submitted without observed repair. | Existing notice, clear, stale, and unavailable behavior remains in force. No additional handoff path is created. |

**Recommendation:** prepare A as the smallest offline experiment. The observed `additionalContext` provider-request inclusion means there is no delivery evidence requiring replacement of that envelope. Stage A leaves prompt interpretation and real-model reaction unresolved, so making the requested action explicit is a testable change within the current advisory Noul policy. Option B is a legitimate, separately reviewable product choice if A fails a future real-host reaction gate or if the owner chooses enforced repair semantics; the offline block arm alone does not justify adopting it. Option C is appropriate if changing advice wording is outside the present issue scope. None of these options makes a Claude support claim today.

## Acceptance contract before another authenticated session

The next work for A is deterministic and offline. Use a controlled `r6_bare_domain_value` positive finding and zero-probability control through the production Claude hook, compiled bridge, resident, and exact `2.1.218` loopback fixture. Require exactly one completed native edit, accepted ticket, `completed-findings`, one classified finding submission, and a second provider request containing the **production** rule reference and the explicit repair request; the first request must contain neither. The no-finding control must return quiet with zero submissions. Assert that the hook output remains valid `PostToolUse` `hookSpecificOutput.additionalContext`, fits the existing output cap, and completes within the 3,900/4,400/five-second bounds. Record source-free timing and booleans only; do not retain prompts, request bodies, source, model text, or credentials.

Offline negative cases must cover notice-only backend failure, terminal clear, `no-work`, stale/superseded snapshot, timeout, resident loss, and a mixed finding/notice batch. Assert no repair request for a notice alone or any non-current finding, no stale replay, no false clear, and no extra model-visible error on timeout. Preserve the existing cooldown, lease/acknowledgement, and current-snapshot handoff rules. A fixture that sees the instruction in the second scripted request establishes **delivery only**; a canned scripted response cannot pass a model-repair gate. For B, if selected later, repeat these cases with exact top-level `decision: "block"` and `reason`, prove notices and failures never block, and separately specify any Stop stage before testing it.

Only after the owner reviews the offline result should a **separately approved**, bounded authenticated Claude gate be proposed. Its minimum comparison is one all-clear control and one finding session on the exact pinned binary, normal authenticated provider/model, disposable repository and isolated profile, controlled offline Hapsland backend, one synthetic native edit per session, a 90-second host ceiling, 2 MB combined output ceiling, existing native hook deadlines, and a durable session ledger that cannot be reset for retries. Stop on version/auth mismatch, ceiling, or failed edit; make no Jev call. Retain only source-free event categories and relative times. Passing requires the initial native call to match the submitting hook, a classified rule-finding submission, a **distinct later model-originated native repair call** after that submission, a completed repair hook, and the expected final file state without harness mutation. A hook return, second provider request, final model statement, or final file state alone is insufficient. Record notice and unknown output counts separately. The existing Stage A allocation is exhausted; this document authorizes no new session. Stage B stale/admission-triggered host-failure tests also remain gated on exact-call admission correlation, as described in the [next-pass proposal](issue-94-next-pass-proposal.md).
