## What exists now

Bend owns a `State` with rounds, work, admissions, dispatch, collection, and a ledger. A step returns either `Advanced{state, commands}` or `Rejected{state, reason}`. Work has stable operation, round, partition, reservation and parent IDs, plus phases `SourceQueued`, `SourceReading`, `Preparing`, `Reviewing`, `AtJev`, and `PendingFinding`. It does **not** contain diagram squares or `from → to` routes. [Canonical state and work](../packages/agent-flow-bend/Canonical.bend#L22-L47), [step result](../packages/agent-flow-bend/Canonical.bend#L492-L507).

The TypeScript adapter validates and projects that Bend state into typed arrays. It exposes work, queue entries, requests, ready advice, leases, delivery, tickets and rounds with IDs. `stepCanonical` exposes the checked after-state, commands and possible rejection. [Projection shape](../src/canonical/adapter.ts#L915-L934), [projection checks](../src/canonical/adapter.ts#L1077-L1145), [step adapter](../src/canonical/adapter.ts#L1207-L1225). The FoldKit replay already saves each event, commands, before projection and after projection. [ReplayStep and replay](../packages/agent-flow-viz/src/canonical-replay.ts#L9-L17), [execution](../packages/agent-flow-viz/src/canonical-replay.ts#L102-L117).

The 13 squares and their labels are view constructs. They mix Bend state, Bend decisions, native facts and an external Jev fact; several squares show multiple projection fields. The current 24 arrows are also declared in the view, with a mixture of event-name tests, command-name tests and before/after tests. [Square mapping](../packages/agent-flow-viz/src/production-flow-view.ts#L119-L150), [arrows](../packages/agent-flow-viz/src/production-flow-view.ts#L151-L178). Thus the view already has the right place for a semantic mapping, but its active-arrow rules are separate, partial handwritten rules.

## What can be inferred at runtime

| Source evidence | What can be inferred mechanically | What the view still has to define |
| --- | --- | --- |
| Same `work.operation` before and after, `kind` changed | A specific work item changed phase. Examples: queued/read/preparing/reviewing/at Jev. | Which phase or queue membership belongs in which square, and whether a phase change means an arrow or an in-place node update. [Work phase projection](../src/canonical/adapter.ts#L1118-L1134), [square details](../packages/agent-flow-viz/src/production-flow-view.ts#L136-L145). |
| Same `operation` moving among `dispatch.pending`, `active`, `running` | A specific job entered or left the preparation queue or began running. This is stronger than comparing total queue lengths: one removal and one addition can leave counts unchanged. | Map each queue location to the queue/preparation squares; decide whether cancellation or settlement is shown as movement, disappearance, or a status update. [Dispatch entries](../src/canonical/adapter.ts#L934-L954), [current count test](../packages/agent-flow-viz/src/production-flow-view.ts#L153-L157). |
| Same request ID changes `started` or disappears | Issued request became observed started, or request tracking ended. | Treat request issue as permission/command, request start as an observed attempt, and settlement by its supplied outcome; disappearance alone cannot identify finding, clear, timeout, interruption or cancellation. [Request projection](../src/canonical/adapter.ts#L946-L953), [request events](../packages/agent-flow-bend/Canonical.bend#L91-L103). |
| Ready advice ID, lease ID, delivery slot or submission batch appears/changes | Stored canonical collection or delivery state changed for that ID. | Identify the business meaning of the change and distinguish reserved, authorized, submitted and uncertain phases. [Collection/delivery projection](../src/canonical/adapter.ts#L927-L932), [current square details](../packages/agent-flow-viz/src/production-flow-view.ts#L145-L149). |
| Round, charge or permit appears/changes/disappears | Capacity, admission or round status changed. | Often show a changed count or square state, not a cross-square arrow. A released charge, for example, does not by itself say where an item went. [Projection shape](../src/canonical/adapter.ts#L915-L925), [Bend capacity commands](../packages/agent-flow-bend/Canonical.bend#L268-L293). |

For an ID created or removed within one atomic step, before/after state may provide only one endpoint. Event and command tags identify the cause and outcome. A step can produce several commands and several state changes, so projection must support **zero, one or several** visual explanations per step. [Bend step shape](../packages/agent-flow-bend/Canonical.bend#L502-L504), [ordered unit commands](../packages/agent-flow-bend/Canonical.bend#L268-L291), [dashboard's within-step capacity frames](../packages/agent-flow-viz/src/production-main.ts#L209-L225).

## Where tags and native facts are necessary

`JevRequestReady` supplies external readiness facts and can emit `JevRequestIssued`. This is authority to attempt a request; it is not evidence that a network attempt started. A later `JevRequestStarted` records the observed attempt, and `JevRequestSettled` supplies the observed result. [Event variants](../packages/agent-flow-bend/Canonical.bend#L91-L103), [command variants](../packages/agent-flow-bend/Canonical.bend#L293-L304), [resident request bridge](../src/resident/capacity.ts#L255-L308). The view already distinguishes a dashed command arrow from an observed attempt arrow. [Route rules](../packages/agent-flow-viz/src/production-flow-view.ts#L159-L166), [legend](../packages/agent-flow-viz/src/production-flow-view.ts#L194-L208).

Likewise, `retainFinding` is a Bend disposition. Actual native advice storage is a separate resident action, and `collectionReady` is a later supplied readiness fact. Showing a stored-advice arrival on `retainFinding` alone would claim too much. [Resident action](../src/resident/server.ts#L2651-L2670), [native readiness call](../src/resident/server.ts#L877-L887), [source-free replay's explicit separation](../packages/agent-flow-viz/src/canonical-replay.ts#L50-L54). A `finishAuthorize` command likewise does not prove host output; delivery phase and later terminal events describe recorded progress. [Delivery projection](../src/canonical/adapter.ts#L932-L932), [showcase events](../packages/agent-flow-viz/src/canonical-replay.ts#L58-L68).

## Static analysis and coverage

A source tool can extract Bend event and command variants and the exhaustive `step` match cases. It can compare those names with TypeScript adapter variants and view classifications. That gives useful **schema and classification coverage**, but Bend branches call functions and can return different commands and state for different inputs. Static names alone cannot infer the business meaning of squares, native effects, or every concrete endpoint. [Bend event/command/result types](../packages/agent-flow-bend/Canonical.bend#L69-L75), [dispatch cases](../packages/agent-flow-bend/Canonical.bend#L2713-L2778), [adapter result](../src/canonical/adapter.ts#L1207-L1225).

Dynamic replay is practical now: replay representative accepted and rejected events through `stepCanonical`, compare typed before/after projections by stable ID, add event/command tags, then resolve those changes through a **single view-level square map**. It proves the traces tested, not every possible reducer branch. The old diagram's exhaustive route check worked because its *own discussion reducer* declared `TRANSITIONS` with `from` and `to`; it was not inferring them from the production Bend reducer. [Old transition table](../packages/agent-flow-viz/src/flow.ts#L62-L86), [old generated coverage](../packages/agent-flow-viz/src/generation.ts#L43-L81), [new replay](../packages/agent-flow-viz/src/canonical-replay.ts#L102-L117).

There is already a static authority check to extend rather than duplicate: `scripts/check-canonical-authority.mjs` compares declared TypeScript event kinds with encoder cases, Bend command constructors with decoder cases and TypeScript command kinds, and compiled Bend tags/exports. It does not currently classify graph placements or route semantics. [Existing check](../scripts/check-canonical-authority.mjs#L23-L49), [remaining checks](../scripts/check-canonical-authority.mjs#L52-L74). In the current showcase, the work and request IDs let a dynamic diff show queued-to-reading, preparation-to-reviewing, reviewing-to-at-Jev, at-Jev-to-pending-finding, request-start flag changes, ready advice and delivery phases; `startReview` is a useful counterexample because the emitted `ReviewStarted` decision may be visible without a tracked state movement. [Showcase sequence](../packages/agent-flow-viz/src/canonical-replay.ts#L22-L68), [command constructor](../packages/agent-flow-bend/Canonical.bend#L293-L300).

An accepted step need not light an arrow. A capacity resize, count update, permit change, in-place phase detail, or decision-only check may best light a node or annotated result. A rejected step should show refusal and no invented movement. The requirement is that every displayed step has a truthful **explanation**, not that it has an arrow. The current UI already shows the event, rejection and commands below the graph; graph coverage should be checked separately from that text. [Step result](../packages/agent-flow-bend/Canonical.bend#L502-L504), [result UI](../packages/agent-flow-viz/src/production-main.ts#L209-L213).

## Proposed view-level contract for #147

Keep square names and positions in FoldKit. Define one typed placement map from projected state/fact categories to squares, and one small set of interpretation rules for event/command facts whose endpoints cannot be read from state alone. Build active graph changes from the checked before/after step plus those tags. Every rule should say whether it denotes stored state, a decision/permission, an observed native fact, an external response, or a native output fact; the renderer can use those categories for distinct lines and labels. Do not add square IDs or route metadata to Bend.

Check: (1) every projected state category used by a square has an explicit placement; (2) every accepted replay step yields a classified state change, tagged fact/decision, or documented no-graph-change reason; (3) rejected steps only explain rejection; (4) all declared arrows have a producing checked trace; (5) event and command variant inventories are exhaustive at the adapter/view classification boundary. This combines a finite dynamic check with static exhaustiveness of the view's vocabulary. It does not assert that fixtures cover every possible Bend path.
