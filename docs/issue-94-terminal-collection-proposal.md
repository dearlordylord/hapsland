# Issue #94: terminal collection contract proposal

**Decision status (2026-09-24):** accepted and implemented for the Claude-only offline path after owner approval. The ticketed v2 admission/collection path is implemented and covered by offline tests; the one selected compiled bridge/CLI/resident cold all-clear control passed. This does not authorize or record an authenticated Claude run, establish host support, or include OpenCode host work, which is postponed at the user's direction. Codex and OpenCode retain their existing v1 paths and behavior.

## Evidence and present gap

The [offline timing investigation](issue-94-timing-investigation.md) first measured two fresh compiled-CLI Claude controls under the 4,400 ms bridge and five-second native limits. In the second, the resident recorded controlled `clear` at 1,857 ms from bridge preload, yet 47 collection calls returned `empty` through 4,397 ms and the bridge timed out. The first had accepted admission but no observed review completion. These selected, instrumented controls located one completed-clear polling failure; they did not establish a cold latency distribution or that every timeout has the same cause. The Claude-only ticketed path described here was subsequently implemented and passed the selected offline control recorded in the timing report and [sanitized result](../evidence/host-94/validation/terminal-clear-cold-result.json).

Before implementation, [`collect`](../src/resident/server.ts) returned `empty` when no advice or notice was selected, whether review was still queued, a clear evaluation finished, advice was not yet eligible, revalidation lost authority, or no work existed. [`collectReady`](../src/resident/client.ts) reduced every non-`advice` response to `undefined`, and the bounded hook polled until advice or its 3,900 ms deadline. A `stats` snapshot is global and cannot prove the outcome for this advicee. The implementation adds ticketed outcome collection for Claude's bounded hook while retaining the v1 collection path for Codex and OpenCode.

## Accepted source-free contract for Claude's offline path

The implemented v2 IPC admission/collection variant is restricted to bounded Claude hooks. An accepted admission returns a **ticket** consisting of an opaque random nonce and the resident lifetime. It is scoped internally to canonical root, host and host version, session, agent (where present), and tool-use ID. OpenCode remains on v1 while host work is postponed; Codex's broader session partition and subsequent-hook collection also remain on their existing v1 path. The ticket is a capability for the exact accepted ingress, not a claim that preparation or review succeeded. Keep its nonce out of logs, activity records, timing evidence, and host output. The status body contains only fixed enum values; it contains no source, path, session ID, tool-use ID, work key, hash, generation, or count. Existing `advice` still carries its established output and lease token, with the existing bounded-output rules.

For `collect(ticket, root, advicee, dispatch, mode)`, validate resident lifetime, ticket ownership, credential generation, and a resident-local admission generation before observing state. The resident tracks the admitted ingress and every descendant unit through a terminal outcome. Once preparation closes, the ticket's unit set is fixed. Registration and completion must occur in the same authoritative resident state, including cached evaluations, capacity rejection after preparation, policy skips, backend/credential failures, supersession, and cleanup. A unit is complete only after any finding has been retained or a final failure has been recorded; a provider completion alone is not enough. A partition notice produced by this admission also belongs to its ticket; if the existing cooldown coalesces notices from several admissions, the ticket must conservatively treat any pending notice in that partition through its collection fence as deliverable before claiming clear.

| Status | Exact meaning and bounded-hook action |
| --- | --- |
| `pending` | Admitted ingress has not closed; at least one unit is queued/running; a successful finding is being retained/revalidated, is within the 50 ms collection window, is leased to another collector, or another deliverable item for this ticket remains. Poll within the existing budget. |
| `advice` | One or more findings and/or an operational notice are ready and leased. This includes notice-only output (`findingCount: 0`). Submit through the current writer, then acknowledge/finalize as today. `advice` takes priority over all terminal statuses. |
| `clear` | Preparation closed; at least one eligible unit for this ticket completed a successful, validated zero-finding evaluation; **all** units for this ticket are terminal successful clear; no finding or notice for this ticket is pending, leased, or being revalidated; no revision **within this ticket** was superseded by the final handoff barrier. This certifies the admitted snapshot's review outcome, not the current contents of the workspace. Return quiet success immediately. Never infer this from an empty advice list, `stats`, an activity file, or a controlled outcome file. |
| `delivered` | All ticket units are terminal without any failed, stale, lost, or expired unit; every resulting finding has been acknowledged and finalized; at least one finding was delivered; and no advice or notice remains pending. Return quietly on a later collection. Never reinterpret delivered findings as clear. |
| `unavailable` with fixed reason `backend`, `credential`, `capacity`, `stale`, `lost`, or `expired` | The ticket cannot prove complete clear. `stale` means superseded work or failed final workspace authority; `lost` covers unknown ticket, resident replacement, lifecycle loss, or missing accounting; `expired` covers retention expiry. If a notice is ready it is returned first. Otherwise return quietly without calling it clear. These reasons are diagnostic only and must not enter host context. |
| `no-work` | The accepted ingress closed with zero eligible units, for example a valid policy/configuration skip, and no pending notice. A missing/invalid ticket is **never** `no-work`. Return quietly. |

Rejected admission is a separate existing admission result and creates no ticket. A rejected or skipped admission must not be interpreted as completed clear. Apply precedence at the final handoff barrier: return leased `advice` first; then `pending` while ingress/units or deliverable items remain; then `unavailable` for **any** failed, stale, lost, or expired unit, even if another unit's finding/notice was already finalized; then `delivered` for a wholly successful ticket with finalized findings; then `clear` for a wholly successful zero-finding ticket; then `no-work` for zero eligible units. Thus a mixed success/failure ticket is `unavailable` after its advice drains, never `delivered`. If output selection leaves eligible findings or notices behind because of response size, return `pending` on the next collection, not `clear` or `delivered`. A failed acknowledgement, expired lease, or disconnected collection keeps the item pending or returns `unavailable` if authority is gone.

### Generation and race rule

Assign an admission generation when accepting ingress, before enqueuing it. Assign unit work revisions as today, then associate each revision and its terminal outcome with that admission. Multiple equal-input members may share a work revision or cached evaluation, but **each admission** needs its own completion accounting. Keep a small bounded tombstone until the ticket can be collected or expires; do not use `#currentWork` absence as proof of clear, since successful clear releases that map entry. Supersession for this terminal claim is **ticket-local**: a newer revision for the same `workSubject` registered before the final handoff barrier makes the older ticket stale, including when registration occurs **after** its successful evaluation and before collection returns. Retain enough revision history or an invalidation flag on the ticket to detect that case after `#currentWork` releases the old entry. The current `workSubject` contains `adviceePartition`, and Claude/OpenCode partitions contain `toolUseId`, so a later tool call has a different subject. Its workspace edit does not retroactively invalidate a successful clear of the earlier admitted snapshot. This proposal deliberately makes no cross-call current-workspace claim and requires no cross-call workspace recapture for zero-finding terminal status. Finding delivery continues to use its existing workspace revalidation. Resident restart/lifetime change yields `unavailable: lost`, never clear. Retention has an explicit deadline and capacity bound; evicting an uncollected ticket yields `lost` or `expired`, not `no-work`.

The collection decision has a **last synchronous handoff barrier** after all awaited revalidation and the test response gate, immediately before response encoding in `#responseForHandoff`. At that barrier recheck ticket lifetime/ownership, its admission generation, all unit completion records and ticket-local supersession flags, credential generation, advice/notice leases, and expiry against one clock reading. Return `advice` if a current deliverable was selected; otherwise compute the status again from current state. No `await` may occur between this decision and `socket.end` issuance. A review that completes during collection is therefore visible in the final snapshot; a finding retained during an awaited revalidation cannot be bypassed by an earlier `clear` decision. If this ticket's unit is superseded before the barrier, invalidate its clear claim; a different tool-use ticket does not invalidate it. The decision is linearized at that barrier; work completing after it belongs to a later observation, and cannot be work whose ticket was already truthfully terminal clear. Deterministic tests should pause at the existing revalidation/response gates to prove both sides of this rule.

## Minimal implementation surface

1. [`protocol.ts`](../src/resident/protocol.ts): implemented the v2 ticketed `admit`/`collect` request and strictly decoded responses, retaining v1 decoding for Codex and OpenCode. Unknown or unsupported ticketed responses do not prove clear. Status payloads contain no advicee IDs.
2. [`server.ts`](../src/resident/server.ts): implemented bounded admission records, ingress and unit terminal accounting, ticket ownership/lifetime checks, and terminal status calculation. Ticket retention is bounded to 600,000 ms and 256 records; eviction cannot prove clear. Existing finding/notice leasing, 50 ms combination window, pending-advice expiry, and response byte/item limits remain in place.
3. [`client.ts`](../src/resident/client.ts): implemented the typed ticketed admission result and `collectOutcome`, preserving `collectReady` for the v1 Codex/OpenCode path. Collection stays bound to the original resident lifetime.
4. [`cli.ts`](../src/cli.ts): Claude's synchronous `PostToolUse` path retains the accepted ticket, submits `advice`, polls `pending`, and returns quietly for terminal outcomes. OpenCode's host path remains on v1 and unchanged; Codex's collection-only flow remains unchanged. Existing fail-quiet deadline behavior is retained.

The protocol version change should be shipped atomically with the compiled CLI and resident. During a mixed-version launch, a v2 request to a v1 resident fails conservatively; an old v1 CLI continues to use its existing `empty` behavior. Do not map v1 `empty` to v2 `clear`. Existing resident data is process-local, so no persistent migration is needed; replacement intentionally loses its old tickets.

## Offline verification and acceptance result

Use deterministic resident/client tests with controlled clocks and gates: queued ingress, delayed clear, cached clear, zero eligible units, completed finding, notice-only failure, mixed clear/failure, finding-plus-failure before and after advice finalization (`unavailable`, never `delivered`), ticket-local stale revision **after clear evaluation but before the final handoff barrier** (`unavailable: stale`), a later separate tool-use edit that does not retroactively change the earlier ticket's terminal result, credential generation change, advice expiry, ticket expiry/eviction, resident restart, wrong root/session/tool-use ID, and old-version response. Test a finding that becomes ready while collection awaits revalidation or the response gate; it must return advice or pending, never clear. Test a clear completion during that same interval; the final response may return clear. Test simultaneous collectors and failed acknowledgement so no leased output is silently cleared. Assert status JSON has no source, path, advicee identifiers, work key, or generation. Ordinary tests remain offline and deterministic.

The implementation and build completed, and deterministic offline tests cover ticketed protocol/client behavior, resident terminal collection, and Claude hook handling. The one bounded scripted Claude cold all-clear control then passed through the compiled bridge/CLI/resident path using a fresh disposable repository and resident. It kept the CLI's 3,900 ms deadline, bridge `spawnSync` 4,400 ms ceiling, and fixture/native five-second ceiling unchanged. It had one matching native edit and completed initial hook, one accepted ticket, controlled successful clear, terminal `clear` after three collection responses, zero host submissions, no repair, and all stated ceilings met. The [sanitized evidence record](../evidence/host-94/validation/terminal-clear-cold-result.json) retains only source-free operation/status/stage timing, acceptance category, and duration. This selected pass closes the offline timing prerequisite only; it is not a general latency guarantee or authenticated host/model reaction. Authenticated Claude Stage A still requires separate owner review and authorization. No Jev call or authenticated host run occurred. OpenCode host work is postponed.

## Implementation decisions and remaining acceptance gap

- Ticket retention is 600,000 ms and at most 256 records; capacity eviction or expiry cannot establish clear.
- After an operational notice is delivered, an associated failed ticket remains `unavailable`; it does not gain a notice-delivered terminal state or become clear.
- A successfully closed ingress with zero eligible units returns `no-work`; failed preparation returns `unavailable`.
- **Stage B exact-admission alias remains open.** The host acceptance marker remains global and unkeyed, so real-host stale and admission-triggered host-failure cases still lack proof tying admission to the exact native call. The separate HMAC alias/test seam described in the [next-pass proposal](issue-94-next-pass-proposal.md) needs owner review and deterministic tests before those Stage B cells can run.
