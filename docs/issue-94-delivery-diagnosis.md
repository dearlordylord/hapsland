# Issue #94: Claude finding delivery diagnosis — 2026-09-24

The Stage A authenticated finding run [completed Hapsland review and submitted a classified rule finding](issue-94-host-validation.md), but no later native repair was observed. That result established a submission boundary, not whether the finding entered another provider request. The offline fixture below tests that narrower boundary with the exact cached Claude Code `2.1.218` host. It does not repeat authenticated acceptance.

## Method and result

Run `node --test evidence/host-94/validation/claude-delivery-fixture.test.mjs` from the repository root after `npm run build`. The fixture requires the cached exact binary at `/home/node/.local/share/claude/versions/2.1.218` and fails if its version differs. It creates a disposable Git repository and isolated Claude profile, enables Hapsland with the compiled production CLI, and asks a loopback scripted Anthropic-compatible provider to issue one native `Write`. The production `--claude-hook --controlled --controlled-writer` path evaluates the synthetic `OrderCount` type using the controlled local backend. The wrapper accepts output only when the production hook completed with the `r6_bare_domain_value` finding. The context arm preserves the production finding and appends a fresh marker. The block arm replaces the full context with a source-free rule reference and the marker. The plain arm emits only the marker on stdout. The marker is absent from the initial prompt and provider request.

The runner observes the parsed **second provider POST**, after the hook's completion status, and reduces its message history to booleans. Request bodies, host JSONL, model text, source, hook output, and credentials remain in memory or the removed temporary directory. The retained records contain only status, timing, byte counts, and booleans. Each run has one host session, an 88-second termination trigger with a 90-second ceiling, and a 2 MB combined host-output ceiling. No authenticated provider or Jev request is made.

The three deterministic tests passed. All runs observed exactly two provider requests, a `completed-findings` controlled backend outcome, a successful hook, a completed synthetic edit, host exit 0, and neither marker nor production finding syntax in the first request. The checks inspect the actual parsed POST body; hook stdout and the host's own stream are not counted as delivery. The context arm's second user message contained both its fresh marker and the production `r6_bare_domain_value` finding syntax. The block arm's user message contained its marker and the wrapper's source-free rule reference; it did not carry the production finding text. The plain control's marker was absent despite exit 0, so plain post-tool stdout is not an equivalent delivery mechanism in this exact headless setup.

**Inference:** Claude `2.1.218` can place the production Hapsland finding's rule text in a subsequent provider request in this synthetic local-provider loop. The authenticated Stage A failure therefore cannot be explained by a universal inability of `additionalContext` to cross this host boundary. It could still reflect model choice, different real-provider handling, session teardown, prompt/review wording, or another condition. The block arm establishes delivery of the alternative envelope's fixture-authored reason only. The fixture's canned final response is not model reaction evidence, and it makes no claim that `decision:"block"` causes a real model to repair the file. The observed intervals are host-local wall-clock differences; they are not model-read latency.

## Product decision boundary

Claude documents that `PostToolUse` block reasons prompt Claude, while `additionalContext` adds context after tool execution. This is `DOC` / `DOCUMENTED` evidence from the [Claude hooks reference](https://code.claude.com/docs/en/hooks#posttooluse-decision-control), accessed 2026-09-24. Mutable documentation does not establish the pinned `2.1.218` runtime contract or authenticated model behavior.

Hapsland's production block reason and repair request reached the next loopback provider POST. Clear was quiet, and a notice remained advisory with block opt-in active. This is `RUN` / `RUNTIME-TESTED` evidence from the controlled fixture above. It establishes provider-request inclusion, not model interpretation or repair. The acting-finding versus notice distinction is a Hapsland feedback choice; [its contract and evidence status](issue-94-claude-block-proposal.md) record that decision.
