# Hapsland direct-event security code map (source inspection, 2026-09-24)

This is advisory evidence for the supported direct-event profile, not a formal proof or a product specification. The [profile](../direct-event-v1-supported-profile.md) limits the supported production path and distinguishes source egress from host delivery. The consent and exclusion decisions are recorded in [ADR 0001](../adr/0001-repository-scoped-backend-consent.md) and [ADR 0002](../adr/0002-accumulate-file-exclusions.md). Claims below come from source inspection only; no runtime test or Jev request was made for this note. Line references are to checkout HEAD `f32acaf8cedef59cf03889f638ce83cfd4476ebb`, with a dirty working tree (including this new note and other concurrent edits).

## High-value questions for specification

1. **What does an exclusion promise?** Current selection prevents a named excluded file from entering filesystem capture and provider input on the preparation path (C3–C5). The hook has already received patch lines and passes them through local IPC (C1, C8). A promise that excluded source is never read by Hapsland would need a narrower adapter/transport design and a precise definition of “read.”
2. **Can an exclusion changed after preparation prevent egress?** The resident reloads settings at evaluation, but the prepared input is made with the earlier policy. At the pre-provider edge, the code checks consent, root and credentials, then calls `evaluatePrepared(job.prepared)` without an explicit re-selection or current-policy comparison. Revalidation with current policy happens before *host publication*, after evaluation. This is a source-inspected temporal gap to test and specify; whether policy changes should revoke queued work is a product decision. [server.ts](../../src/resident/server.ts#L1080), [server.ts](../../src/resident/server.ts#L1250), [server.ts](../../src/resident/server.ts#L1319), [server.ts](../../src/resident/server.ts#L1428)
3. **What is the disk claim?** User-facing wording should enumerate consent, source-free status/receipt/diagnostic metadata, demo traces when used, and startup diagnostics (C9–C10). The debug exception is especially worth a bounded inspection with a synthetic source marker. Do not infer provider-side retention from the application code.

## Smallest code-connected verification seam

Start with a pure authorization decision immediately before `DecisionModel.decide`: `(current consent identity, current resolved policy, prepared relative path, prepared input identity, credential authority) -> allow/deny`, where deny is the safe default. Reuse the same path-selection predicate used before capture, and make the accepted decision observable to an offline controlled `DecisionModel`. Model the small state transition system around prepare → config/consent mutation → dispatch; then generate trace cases against the production gate, including “include then exclude before dispatch,” “revoke consent,” path aliases/symlinks, and concurrent queued units. The existing `preparedProviderInput` function is the egress payload seam; compare its exact JSON value to an allowlisted shape with synthetic markers. Instrument local write sinks separately. A model of path selection alone would miss the queued-work interval shown above.
