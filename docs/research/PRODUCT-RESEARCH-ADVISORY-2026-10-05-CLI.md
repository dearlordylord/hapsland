# CLI help and interface patterns

**Purpose:** Compare practical help and script-interface patterns for Hapsland’s local rules CLI.
**Status:** Product-specification advisory; temporary research report.
**Authority:** Advisory evidence only. Accepted rule and configuration contracts remain in their named specification owners; this report does not approve a new dependency or feature.
**Expected use:** Inform the rules CLI help/interface improvement and identify later decisions for JSON output, editor support, and shell completion.
**Lifecycle:** When the CLI help/interface improvement milestone is accepted, transfer adopted contract decisions to [`docs/review-contract-compatibility.md`](../review-contract-compatibility.md#configuration-and-individual-rules) and the user-facing command guidance to [`docs/configuration.md`](../configuration.md), update inbound links, then delete this report. Keep no separate research snapshot; unadopted findings remain in Git history.

## Research brief and change log

Research question, 2026-10-05: how should `hapsland rules` help people discover actions and make the CLI dependable for humans, scripts, and agent runtimes? Here “API” means the command grammar, JSON output, and rule/config files; Hapsland’s HTTP endpoints are outside this request. The current baseline is Effect CLI 4.0.0, version-one JSONC config/rule files, local reversible rule changes, and rules that are edited as JSON files. An installed Hapsland CLI, shell completion, or in-app editor is not assumed.

Representative workflows are: discover available actions from `rules --help`; learn the flags for one action; copy an example; inspect a rule and its path/language selection; create, connect, enable, or disable a rule with explicit identity/path and scope; and consume `--json` from a script without interpreting human prose. Hapsland’s broader post-edit advisory/blocking behavior, multiple installed-agent setup, and Jev failure path are outside this CLI boundary; rule management makes no classifier calls. The rules command is agent-host neutral. The existing-solution baseline is the Effect CLI already used by Hapsland. Evidence that would overturn it is a pinned-version limitation that prevents command-specific help or requires maintaining a separate help inventory.

Discovery queries targeted official sources: `Effect CLI Command.withSubcommands/withExamples`, `Git git-help`, `GitHub CLI --json/editor/prompt`, `kubectl command reference/explain/completion`, and GNU `--help` plus POSIX utility syntax. Package registries, agent-host extension catalogs, issue trackers, and general CLI-framework comparisons were excluded because no new dependency or host integration was under consideration. The initial pass selected primary references from POSIX/GNU guidance, Git, GitHub CLI, kubectl, and the Effect v4 API. A second pass checked exact APIs and stream/editor/completion behavior. Two passes found no materially different interface class; this is a targeted CLI-pattern comparison, not a survey of every CLI framework. No third discovery pass was made.

At base commit `37417c7f17aa876aa992180683cdd32b659e7448`, `packages/administration/src/cli-command.ts` represented rule actions as one optional `Argument.Literals` positional and shared all rule flags. `packages/administration/src/rules/command.ts` defaulted a missing action to `list`. During this research, the shared worktree gained an uncommitted `packages/administration/src/rules/cli-definition.ts` command catalog, child commands, focused help, and generator wiring. That code is recorded below as source-inspected evidence, not as an accepted requirement or a result independently validated by this research pass.

Do not add a parser or API dependency. Defer integrated editor support and completions until a distinct product decision and acceptance check exist. ## Synthesis, sufficiency, and disconfirmation

The strongest convergent practice is that the executable command structure owns its help. Git and kubectl expose action names and descriptions at the parent level; Effect can generate that listing from child commands. GitHub CLI and kubectl also teach through examples and provide a distinct structured output path for scripts. This directly supports replacing the old optional action literal with actual commands and generating docs from the same source.

The current worktree’s metadata catalog already applies that recommendation: its command names, descriptions, flags and examples build the parser tree; the docs generator reads that tree through `ruleCommandReference()`. This is the minimum useful change for the discovered gap. Final acceptance still depends on the repository’s selected local CLI and docs checks; source inspection is not test evidence.

Keep `rules` focused on local rules. The accepted rule workflow already makes mutation intent explicit through the action name and requires `--scope` for unattended changes. This pass recommends no extra blanket `--yes`/`--apply` flag: `--scope` selects the target configuration, and adding another confirmation token to these reversible local writes would add friction without evidence that the existing contract is inadequate. The separate setup flow’s `--apply` rule covers broader installation changes and should not be generalized to rule toggles. [E10]

The help can point to `show` and the displayed source file for editing. If an editor command is later accepted, consider conventional `VISUAL`/`EDITOR` settings and an optional `HAPSLAND_EDITOR`; do not adopt GitHub-specific `GH_EDITOR` or `GIT_EDITOR` variables as Hapsland settings. `gh` is evidence that editor choice is useful CLI configuration, not that its app-specific variable names should transfer. Launch safely and validate the edited rule. This remains optional integration work. [E4, E10]

The existing solution is sufficient for the present need: Hapsland already depends on Effect and its v4 command tree supports the required discoverability without another library. The strongest case against leaning on Effect’s help surface is API instability: future Effect upgrades could alter help or parsing behavior. The response is to keep the package cohort pinned and test the app-owned contract (action names, descriptions, examples, flags, default behavior) rather than assert exact formatter spacing. Reconsider the approach if a pinned Effect upgrade cannot preserve those checks without app-specific formatter replacement. [E6–E7]

One unresolved technical boundary is parse-error output outside the cases already selected. Current Effect v4 docs/source describe help and error formatting, but the source revision checked by the supporting survey was not verified against this repository’s exact `effect@4.0.0` artifact. The project owner reports focused subprocess/smoke checks verifying empty stdout for missing, duplicate and irrelevant flags and unknown rule IDs; this research did not independently replay them. Do not extrapolate those results to every parse error or promise empty stdout for all invalid invocations with `--json`. Script consumers should check exit status before parsing stdout. Broader stream/exit behavior remains deferred to a pinned-version fixture if the CLI contract needs it.

## Limitations, stopping condition, and primary-source index

This research is limited to the cited primary documentation and the local Effect/Hapsland sources listed in the evidence ledger. It does not measure users, run shell completion installation, test editor launch behavior, define every CLI exit code, or audit all `--json` payloads. The current command implementation was changing during the pass; its state is source-inspected and should be judged by the project’s actual local checks. Two discovery passes produced no materially different CLI practice, so discovery stopped without claiming ecosystem completeness.
