# Hapsland setup interaction model advisory

**Purpose:** Compare explicit models for Hapsland's interactive setup conversation and record evidence for a later design decision.
**Status:** Temporary product-specification advisory; no product behavior or dependency is adopted.
**Authority:** Advisory research, source inspection, and design inference. Existing setup, installation, credential, and consent contracts remain authoritative; this report is neither an accepted product contract nor implementation validation.
**Expected use:** Use the candidate comparison, proposed typed model, and traceable questions to choose a prototype and later amend the owning setup and configuration contracts.
**Lifecycle:** Temporary until the setup-interaction design acceptance milestone. At that milestone, consolidate the selected architecture into an ADR and adopted behavior into `docs/installation-workflows.md` and `docs/configuration.md`, update inbound links, and delete this report. Git history retains research evidence and rejected options.

## Research brief

**Date and question.** 2026-10-06. Should Hapsland setup remain an imperative Effect sequence, gain an inspectable typed reducer with Effect commands, use a statechart/actor library, or use a durable workflow engine? Which interaction patterns help users choose runtimes and credential destinations, review consequential writes, go back, cancel, recover, and understand partial completion?

**Scope.** This pass covers the interaction controller and its relationship to the existing version-one setup engines. It does not design a replacement for hook ownership, configuration, credential persistence, installation journals, paid-request budgets, or Bend-owned review policy. The controller may request those existing operations and react to their observations; it must not duplicate their write logic or decide review eligibility. Terminal rendering is a separate research pass at [the console-rendering advisory](PRODUCT-RESEARCH-ADVISORY-2026-10-06-CONSOLE-RENDERING.md).

**Current assumptions and baseline.** This worktree is at repository commit `16439f1d00583f501004662ddd3a126b38c5b260`. `package.json` pins `effect` and its companion Effect packages to `4.0.0`, TypeScript `7.0.2`, and Bun `1.3.14`. The existing baseline is the current Effect generator/branch flow plus the typed version-one setup request/result, digest-bound installation and rules operations, the current terminal selector, and the unattended JSON/save-plan interface. A small local reducer over these existing operations is the no-new-dependency alternative.

**Representative workflows.** Initial human setup selects one or more of Claude Code, Codex CLI, and Pi; existing registrations start checked, and each profile has its own preview/approval and may partially apply. A user may keep an available higher-precedence environment or file credential, enter a missing or replacement saved credential through masked input, defer setup, or choose a destination only if that design is later accepted. Any paid Jev check is separate, explicit, bounded, and may fail without invalidating saved setup. Unattended preview/apply/save-plan is already a separate explicit path and must remain free of menus and implicit approval. Re-entry after cancellation, stale previews, partial writes, EOF, Ctrl+C, process interruption, or failed verification must preserve clear ownership and next steps.

**Targets and evaluation questions.** Target is TypeScript on bundled Bun `1.3.14`, with Effect `4.0.0`, and runtime-neutral interaction across Claude Code, Codex CLI, Pi, and later adapters. Compare inspectable legal transitions; separation of pure state decisions from filesystem, credential, terminal, and network effects; cancellation and recovery; digest-bound consent; secret exclusion from state and logs; multiple profile orchestration; testability/graphability; compatibility evidence; and the ongoing cost of adding a framework.

**Existing-solution and disconfirmation baseline.** Compare against (1) current Effect orchestration, (2) a typed discriminated-union reducer whose transitions return command descriptions interpreted by Effect, and (3) existing version-one setup/save-plan engines. A framework recommendation must show a material capability beyond these. `effect-machine@0.28.0` is the discovered exact-Effect-4 package candidate for that comparison, not an adopted dependency. Change the no-new-dependency preference if an exact-target prototype shows that its state/event model and Effect tasks make critical branches clearer or reduce transition defects without weakening digest ownership, secret handling, headless behavior, packaging, or upgrade control. Reverse it against a durable workflow only if setup becomes a persisted, cross-process operation with an explicit store/retention contract that existing recovery does not satisfy.

**Discovery plan and bounded stop.** Round 1 searched first-party Effect v4 documentation and package source, XState/Stately documentation and release records, Elm's architecture guide, Robot3's repository, and CLI/service design guidance. Query themes were “Effect v4 workflow/state machine,” “Effect cli Prompt,” “XState v5/v6 TypeScript actor,” “Elm model update commands,” “functional finite state machine TypeScript,” “CLI prompts TTY confirmation,” and “back/check answers/change answers.” Round 2 checked the runtime boundary between Effect Prompt, durable Workflow/WorkflowEngine, statechart/reducer models, and multi-step transaction guidance. A review then identified a specific unresolved question about an Effect machine API, so a narrow primary-source addendum checked the v3 experimental Machine module, the exact v4 export map, and current Effect-compatible machine packages. That addendum found `effect-machine@0.28.0`, a dedicated community Effect 4 candidate, and revised the candidate set. Stop this addendum after confirming its exact peer range, source commit, API surface, and package-development toolchain; do not claim ecosystem saturation. Redux Toolkit, event-sourcing frameworks, and hosted orchestrators were not individually evaluated because they add store or distributed-operation scope with no evidenced advantage for a single local CLI run. The companion console-rendering advisory is complete and owns the renderer comparison.

**Candidate inclusion and classification.** Included: repository-local typed reducer plus Effect commands (direct baseline); `effect-machine@0.28.0` (dedicated Effect 4 state-machine and actor package); XState v5 (general-purpose typed statecharts and actors); Robot3 (small functional finite-state machine); Elm's Model/Update/View and command pattern (architecture to borrow, not a TypeScript dependency); Effect `Workflow`/`WorkflowEngine` (durable operation model); and Effect `cli/Prompt` (leaf terminal interaction, not a setup-flow model). The v3-only `@effect/experimental/Machine` and `@handfish/effstate-v4` are recorded as incompatible/excluded for this pinned Effect 4 cohort; XState v6 is noted only as pre-release evidence. Web UI libraries and hosted workflow services are excluded as direct dependencies because setup currently runs locally in one foreground process and needs terminal/OS credential access. Compatibility is evaluated against exact package peer metadata and source evidence; no candidate is considered app-compatible until the required target-runtime checks pass.

## Current setup behavior and authority boundaries

The current terminal path uses `packages/cli-entry/src/cli.ts` to inspect supported client registrations, opens `packages/administration/src/onboarding/client-selection.ts`, and runs `packages/administration/src/onboarding/pilot.ts` once for each selected host. Existing installed hosts are checked by default; unchecking skips that host and does not remove hooks. The loop is sequential. Each pilot first invokes `runSetup` to inspect/preview, shows the proposal, asks for confirmation, then re-invokes the same version-one setup engine with the exact install and default-rule proposal digests. It activates the package after completed or partial installation, reports credential and repository status, may offer the separate bounded Jev check, then runs offline doctor. The unattended command, JSON plan, and digest validation remain owned by their existing paths.

The engine in `packages/administration/src/onboarding/setup.ts` owns per-host compatibility and installation observations, rules preview/application, credential resolution and saved credential writes, repository settings, and setup action digests. Host-specific install modules own hook proposals, ownership checks, writes, and partial recovery. The interaction controller should carry host IDs and opaque proposal digests through a human approval decision, then call those APIs. It must not reconstruct host-file writes, reimplement credentials, synthesize review-policy decisions, or make a successful setup status imply that native host trust or a real review was observed. Bend remains the sole authority for its existing review-policy transitions.

The proposal can add back/branch choices, but the parent flow is not accepted. A session-level client and credential choice could be rendered as one guided conversation, or the current client-by-client progress could remain primary while only repeated credential questions are consolidated. The latter preserves today's per-host approval behavior most closely; the former needs a concrete rule for independent profile failures and approvals. Do not convert “shared session” into a shared write transaction: selected hosts still have different digest owners and can succeed or fail independently.

Evidence from current sources (SRC/SOURCE-INSPECTED unless stated otherwise):

- `package.json` and `bun.lock` pin Effect 4.0.0, TypeScript 7.0.2, and Bun 1.3.14; this establishes project intent and lock metadata, not runtime compatibility with an uninstalled candidate.
- `packages/cli-entry/src/cli.ts` selects hosts, inspects status, then loops through hosts sequentially. The loop records a per-host failure and continues to later hosts.
- `packages/administration/src/onboarding/client-selection.ts` maps Escape to an empty result, Enter to the currently selected list (which can also be empty), Ctrl+C to exit code 130, and input end/error to failure. The caller currently prints “No clients selected” for an empty list, so Escape and an explicit empty selection are not distinguished in the current terminal conversation.
- `packages/administration/src/onboarding/pilot.ts` binds install/rule consent to digests, stops when approval is declined, and launches verification after setup only through its separate port.
- `packages/administration/src/onboarding/setup.ts` applies a write only when the supplied digest matches the current preview and preserves a digest for partial recovery. Credential input is injected as a short-lived callback; the UI/model should not retain the key.
- `packages/administration/src/credentials/masked-input.ts` reads from `/dev/tty`, disables echo, and restores terminal mode in a resource finalizer; `packages/administration/src/onboarding/confirmation.ts` defaults a non-`y` answer to decline and treats prompt failure/cancellation as an error.
- `docs/installation-workflows.md` is maintained guidance for existing guided and unattended behavior. It states that each selected client has its own change preview and confirmation, automation requires explicit choices/apply, and saved plans revalidate current digests. This source is the contract baseline; the 2026-10-06 design proposal is not adoption.
- `docs/typescript-decision-boundary-ledger.md` and `packages/agent-flow-bend/PROOF.bend` establish the existing boundary that native effects/observations are supplied by TypeScript while canonical review-policy transitions remain in Bend.

No candidate package was installed. No typecheck, candidate compatibility smoke test, TTY simulation, or user study was run in this research pass. In particular, local source inspection of pinned Effect 4.0.0 does not validate its prompt behavior under bundled Bun 1.3.14 or nonstandard terminals.

## Candidate cards

### Typed reducer plus Effect command interpreter (repository-local baseline)

**Identity and intended use.** A small Hapsland-owned TypeScript model; no new package. The pure transition function receives one typed event and model and returns the next model plus command descriptions. A separate interpreter turns commands into Effects that call the current version-one setup, activation, credential, verification, and doctor owners. This is the proposed architecture, not implemented behavior.

**Lifecycle and contract.** Events cover setup-session input and sanitized engine observations. Commands represent only requests to existing owners, such as inspect clients, preview a host, apply the exact install/rules digests supplied by that host's preview, activate, resolve credential status, and request an explicitly consented bounded check. Credential capture and persistence remain inside the current credential boundary. If a future design adds credential destinations, the UI must first receive a sanitized save proposal from its owner, show the write and its scope, wait for explicit approval tied to that proposal, and only then prompt/save through that same owner; the destination choice itself is not consent. The reducer never directly performs I/O. A host preview or credential result is displayed as an observation; it does not authorize writes by itself. This keeps the setup engine's proposal and digest protocol canonical.

**Failure, state, and composition.** A command result returns as another event. The model can distinguish waiting, declined, cancelled, interrupted, partial, conflict, failed, and complete outcomes. Each selected host keeps its own observed summary and approval digest. Effects remain sequential initially; the reducer does not need parallel actors. Do not serialize the live model by default: the version-one save-plan flow and installation journals already own the supported cross-invocation handoff and partial recovery.

**Security, portability, and operations.** Store only host identity, source labels, sanitized outcomes, and opaque digests. Any short-lived key capture belongs inside the existing masked-input/credential adapter and owner call, not in a model state, event, command trace, plan, log, or output. Never include raw network bodies or arbitrary engine payloads in UI state. The code remains runtime-neutral and uses already pinned Effect 4.0.0. Its cost is implementing and reviewing the event map, renderer binding, and tests; no candidate package compatibility risk is added. `INFERRED`: this is the simplest default while the workflow remains a bounded foreground CLI sequence and engine owners remain stable; `effect-machine@0.28.0` is the dedicated package that must be compared before fixing the implementation choice.

**Classification.** `BORROW` the Model/Update/View and commands pattern; implement the minimum Hapsland state union locally if it remains the clearest option after a bounded comparison with `effect-machine@0.28.0`. Keep the implementation small enough that states correspond to meaningful user/engine gates, not every line in `runSetup`.

### `effect-machine@0.28.0` Effect 4 state machines and actors

**Identity and intended use.** A community package with a dedicated state-machine API, published as `effect-machine@0.28.0` on 2026-10-01 from git head `176697cf20006f5f539bf04ff2e609bfe1563e22`. Its exact package metadata declares peer `effect >=4.0.0 <5`; the repository manifest at that commit pins its own development `effect` to `4.0.0` and TypeScript to `7.0.2`, includes Bun test scripts, exports the local `effect-machine` entry point, and documents MIT licensing in the README. Sources: [published source README](https://github.com/cevr/effect-machine/blob/176697cf20006f5f539bf04ff2e609bfe1563e22/README.md), [published package manifest](https://github.com/cevr/effect-machine/blob/176697cf20006f5f539bf04ff2e609bfe1563e22/package.json), and read-only exact-version registry metadata summarized in `IM-14`.

**Lifecycle and contract.** The README defines state and event schemas, typed actors, synchronous state/event transitions, Effect-backed `.task` operations that emit success/failure events, `Machine.spawn`/`Machine.run`, and a parent-machine pattern for interactive multi-phase navigation and child actors. This is the strongest dedicated package candidate found for an Effect 4 setup controller. A Hapsland machine could model the shared selected-host session and per-host observed outcomes, while using a task only to call existing v1 engine ports. UI events (selection, back, consent, cancel) and sanitized engine observations should remain distinguishable. The actor does not become a hook, credential, or review-policy owner.

**Failure, cancellation, and security.** The package documentation says a task is scoped to its current state and is interrupted when that state exits; interruption does not emit the typed failure event. Typed Effect failures can map to explicit events, but defects stop the actor or enter supervision. This may support safe cancellation of preview/read work, but interruption of an owner operation does not mean a file write rolled back: disable navigation once a write starts and consume the existing owner's partial/recovery observation. The event/state schemas, actor snapshots, and inspector do not enforce secret exclusion; no credential value may enter them, and inspection/durability should remain disabled unless separately reviewed. Apply digests stay in the awaited-consent state and are passed unchanged to the v1 owner only after the user event.

**Portability and maturity.** The package's own development tree uses Effect 4.0.0 and TypeScript 7.0.2, and its docs show Bun-based tests; this is stronger compatibility evidence than a broad peer range alone. It is still a 0.x dependency with a recent release and no Hapsland install, typecheck, production-bundle, TTY, cancellation, or Bun 1.3.14 execution in this pass. The package supports more actor, persistence, supervision, cluster, and inspection concepts than this foreground flow may need. Those features increase review and future-upgrade scope if the local model only needs a small serial transition table.

**Classification.** `OPTIONAL INTEGRATION` for a one-to-one prototype of the session model; do not adopt from docs or peer metadata alone. `REJECT` its persistence/cluster adapters as a replacement for existing v1 saved plans and installation journals. Compare it against the local reducer using the same events, digest guards, errors, secrets boundary, headless split, and two-host behavior.

### Effect v3 `@effect/experimental/Machine` (incompatible package lineage)

**Identity and intended use.** Effect's v3 experimental package did publish a dedicated effectful `Machine` API. The v3 source defines state, typed public/private procedures, `Machine.make`, `Machine.boot`, and actors that accept requests, run procedures, and publish state. As of 2026-10-06, `@effect/experimental@0.61.1` remained published and still exported `./Machine`; its peer dependency was `effect ^3.22.1`. Sources: [Effect v3 `Machine.ts`](https://github.com/Effect-TS/effect/blob/v3/packages/experimental/src/Machine.ts) and [exact package metadata](https://www.npmjs.com/package/@effect/experimental/v/0.61.1).

**Compatibility and caveat.** The peer range excludes the pinned Effect 4.0.0 dependency, so this module cannot be treated as compatible just because it was an Effect machine. A first-party repository [issue #6069](https://github.com/Effect-TS/effect/issues/6069) records a v3 local actor case in which serializable tagged requests pulled `HttpClient` into the requirements channel; that is a v3 design caveat, not evidence about the newer package or Effect 4.

**Classification.** `REJECT` this v3 module for the pinned cohort. Its existence is part of the search result; its API and limitations do not transfer to Effect 4.0.0.

### XState v5 statecharts and actors

**Identity and intended use.** `xstate@5.33.2`, MIT, the current stable release returned by npm registry metadata on 2026-10-06; current first-party v5 docs require TypeScript 5.0 or later. XState models finite state machines, hierarchical statecharts, actors, invoked async work, and graph utilities. `xstate@6.0.0-alpha.64` was the registry alpha at the same date; the docs recommend v5, so v6 is not a production candidate here. Sources: [v5 docs](https://stately.ai/docs), [invocation](https://stately.ai/docs/invoke), [v5 setup and typing](https://stately.ai/docs/setup), [v5 TypeScript guidance](https://stately.ai/docs/typescript), [exact 5.33.2 package metadata](https://www.npmjs.com/package/xstate/v/5.33.2), [release history](https://github.com/statelyai/xstate/releases).

**Lifecycle and contract.** A machine declares states, typed events, guards, and transitions; an actor runs it, receives events, emits snapshots, and may invoke Promise-based actors with explicit completion/error transitions. The repository describes `xstate` as the full statechart/actor package and `@xstate/store` as a small event store; these are different scopes. History states and graph/path utilities can help inspect richer workflows. For Hapsland, an invoked actor would be a wrapper around the existing Effect owner, not the new owner of file writes.

**Failure, state, and composition.** Actor invocation gives a separate completion/error event path, and machine state can represent nested stages. The available evidence does not establish how cancellation, `AbortSignal`, Effect interruption, stale setup digests, terminal EOF, or Hapsland partial writes compose in this CLI. Actor snapshots and graph utilities are not a substitute for the current setup engine's durable journal and explicit save-plan contract. One actor per host might express concurrency, but concurrent terminal output and shared credential prompts would become new product behavior rather than a free library benefit.

**Security, portability, and operations.** Statechart events/context are ordinary data; XState does not enforce Hapsland's no-secret rule or consent digest ownership. MIT license and current release metadata are documented. Registry metadata did not provide an `engines` or peer dependency constraint for `xstate@5.33.2`; this does not prove support under Bun 1.3.14, TypeScript 7.0.2, or integration with Effect 4.0.0. No install, bundle-size check, typecheck, execution, or terminal run was performed. The XState repository also says it may change types in minor releases, so exact lock pinning and careful upgrade review would remain required.

**Classification.** `REJECT` `xstate` as the runtime owner for the current guided setup. `BORROW` explicit statechart vocabulary and graph/path inspection as a design aid. Reconsider a runtime dependency if the model grows nested/parallel paths, long-lived actors, or a designer-owned workflow that the local reducer no longer explains clearly. XState v6 alpha is `REJECT` for the target release.

### Robot3 functional finite-state machine

**Identity and intended use.** `robot3@1.4.0`, BSD-2-Clause, latest registry release on 2026-10-06. Its first-party repository calls it a small, functional, immutable FSM with `createMachine`, `state`, `transition`, and `interpret`. Sources: [repository](https://github.com/matthewp/robot), [exact package metadata](https://www.npmjs.com/package/robot3/v/1.4.0).

**Lifecycle and contract.** The library makes transitions explicit and gives an interpreter to notify a consumer when state changes. The evidence reviewed here does not show a benefit for this setup flow beyond the local reducer's typed event/state union, nor enough Hapsland-specific evidence about error, cancellation, nested/parallel flow, or Effect integration to justify coupling.

**Failure, security, and portability.** Runtime behavior with Bun 1.3.14 and TypeScript 7 is `UNKNOWN`; no package was installed. The machine would still require an external policy for secrets, consent, stale digests, saved plans, and partial writes. BSD-2-Clause metadata is known, but that is not a compatibility or maintenance conclusion.

**Classification.** `REJECT` Robot3 as a runtime dependency for this use. `BORROW` the minimal immutable transition pattern only where it helps keep the Hapsland reducer pure; a direct local discriminated union is simpler to inspect alongside the repository's exact setup contracts.

### Elm Model / Update / View and commands

**Identity and intended use.** Elm's first-party guide describes an architecture pattern, not a TypeScript package recommendation. Sources: [The Elm Architecture](https://guide.elm-lang.org/architecture/), [commands and subscriptions](https://guide.elm-lang.org/effects/), and its [HTTP example](https://guide.elm-lang.org/effects/http.html), accessed 2026-10-06.

**Lifecycle and contract.** The pattern separates a model, an update function over messages, and a view. When external work is needed, an update returns a command for the runtime to interpret; completion becomes a new message. This maps directly to `transition(model, event) -> { model, commands }`, `render(model)`, and an Effect interpreter. A reducer remains deterministic even while its command executor uses the Effect runtime for async work.

**Failure, state, and composition.** The guide's architecture does not itself prescribe persistence or CLI cancellation semantics; Hapsland should model errors and cancellation events explicitly and keep durable handoff in existing owners. The pattern does not require Elm, browser DOM, or an external dependency.

**Security, portability, and operations.** TypeScript does not give Elm's compiler guarantees automatically, so discriminated unions, exhaustive handling, narrow sanitized observations, and meaningful transition checks must supply them. This is a modest implementation cost with low package risk and a direct fit to Effect command execution.

**Classification.** `BORROW` the model/update/view/command split; do not adopt the Elm runtime or renderer.

### Effect 4 `Workflow` and `WorkflowEngine`

**Identity and intended use.** Modules exported from the project's exact `effect@4.0.0` package. The first-party API calls `Workflow` a durable workflow definition, with schema-described payload/success/error, stable tag, idempotency key, execute, poll, interrupt, resume, registration, suspension, and compensation. `WorkflowEngine` provides in-memory support useful for tests/local development; a durable engine implementation is required for persisted state. Sources: [Workflow API](https://effect.website/docs/v4/api/effect/workflow/Workflow), [WorkflowEngine API](https://effect.website/docs/v4/api/effect/workflow/WorkflowEngine), [exact package page](https://www.npmjs.com/package/effect/v/4.0.0). Existing local declarations under `node_modules/effect@4.0.0` confirm `effect/workflow` exports these APIs. The API is explicitly marked unstable.

**Lifecycle and contract.** This facility models restartable execution and durable activities, not a foreground user navigating setup choices. It could represent machine-observable work that outlives a process, but terminal questions still need a human-interaction surface and rules for waiting, reattachment, sensitive data retention, and approval expiry. Async sequencing in `Effect.gen` is also not a durable workflow: Effect's own guide says an Effect describes work until the runtime interprets it, while Workflow adds execution identity, engine state, and resume semantics.

**Failure, state, and security.** Durable re-entry is valuable when the operation has an accepted storage and restart contract. This Hapsland operation already has explicit save-plan digest revalidation and owner-specific partial-install journals. Persisting UI state would broaden retention to host status, file paths, approval context, and possibly secrets unless rigorously excluded; a live key must never enter a workflow payload or journal. There is no evidence that an additional workflow engine would improve existing recovery.

**Portability and operations.** Exact source-level API availability is confirmed against the pinned Effect 4.0.0 dependency, but target Bun runtime behavior was not executed. The built-in memory engine cannot by itself establish process-restart durability. Introducing this module would also create new persistence, idempotency, migration, cleanup, and human wait/resume responsibilities.

**Classification.** `REJECT` Effect `Workflow` as the interactive conversation model today. The current operation is foreground and the engines already own their durable recovery points. Reconsider only if accepted requirements need a setup operation to survive process exit and continue without a fresh CLI invocation, and after specifying a durable store and secret/retention policy.

### Effect 4 `cli/Prompt` (leaf interaction runner)

**Identity and intended use.** `Prompt` is in the already pinned `effect@4.0.0` package and is exported through `effect/cli`; the project-shared installed package is exactly 4.0.0. Its API is marked unstable. The v4 docs describe `Select`, `MultiSelect`, `Confirm`, `Hidden`/`Password` (yielding `Redacted`), `Custom` render/process/clear handlers, prompt composition, and a `Terminal.QuitError` outcome. Sources: [Prompt API](https://effect.website/docs/v4/api/effect/cli/Prompt), [exact package page](https://www.npmjs.com/package/effect/v/4.0.0), [first-party source](https://github.com/Effect-TS/effect/blob/main/packages/effect/src/unstable/cli/Prompt.ts).

**Lifecycle and contract.** A prompt resolves one value and has its own local keyboard/render loop; `Prompt.all` and `flatMap` sequence prompts. `Custom` can receive external events and re-render. This is useful for a specific question or menu, but a chain of prompt combinators does not by itself make the whole setup journey's engine observations, approval guards, profile results, and recovery branches independently inspectable. The prompt layer should report `Cancel`/quit back to the setup model rather than decide setup outcome.

**Failure, secrets, and portability.** `Hidden`'s declared output is a `Redacted` value, a useful leaf boundary for masked entry, but the surrounding command executor still must prevent the value from entering UI model, event logs, saved plans, or output. The exact 4.0.0 package contains the API and subpath export. The official API docs returned a current 4.0.1 view during this pass, while marking these exports `Added in v4.0.0`; source-level confirmation came from the exact installed 4.0.0 package. No Bun, TTY, EOF, signal, resize, CI, or non-color run was performed. The console-rendering advisory owns suitability for Hapsland's actual terminal constraints.

**Classification.** `OPTIONAL INTEGRATION` for leaf prompt implementation, not for workflow state. Because this code would be in the pinned dependency already, the question is using the unstable API rather than adding a package. Adoption still requires an isolated Bun 1.3.14 prototype covering TTY and cancellation paths and the renderer agent's review of output behavior.

### Candidate typed interaction contract

The following is an illustrative, advisory interface for the local reducer. It deliberately exposes no key value and delegates every mutation to its existing owner. `CredentialDestination` remains a design choice from the temporary proposal, so its cases would need an accepted storage contract before implementation.

```ts
type CredentialDestination =
  | { readonly kind: "project-file"; readonly root: string }
  | { readonly kind: "user-file" }
  | { readonly kind: "native-store" }
  | { readonly kind: "defer" }

type ApprovalSummary = {
  readonly owner: SetupClient
  readonly kind: "installation" | "rules"
  readonly digest: string
  readonly changes: readonly string[] // sanitized display summary only
}

type ProfileOutcome =
  | { readonly tag: "not-started" }
  | { readonly tag: "inspecting" }
  | { readonly tag: "awaiting-approval"; readonly approvals: readonly ApprovalSummary[] }
  | { readonly tag: "applying"; readonly approvals: readonly ApprovalSummary[] }
  | { readonly tag: "partial"; readonly recovery: readonly string[] }
  | { readonly tag: "needs-action"; readonly nextSteps: readonly string[] }
  | { readonly tag: "complete"; readonly readiness: "observed" | "unknown" }
  | { readonly tag: "failed"; readonly code: string; readonly nextStep: string }

type SetupContext = {
  readonly revision: number
  readonly selected: readonly SetupClient[]
  readonly active?: SetupClient
  readonly results: Readonly<Partial<Record<SetupClient, ProfileOutcome>>>
}

type Pending = { readonly commandId: number; readonly revision: number }
type CredentialSavePreview = {
  readonly destination: CredentialDestination
  readonly digest: string
  readonly changes: readonly string[] // sanitized summary from the credential owner
}

type SetupStep =
  | { readonly tag: "selecting-clients"; readonly choices: readonly ClientChoice[]; readonly selected: ReadonlySet<SetupClient>; readonly cursor: number }
  | { readonly tag: "previewing-profile"; readonly client: SetupClient; readonly pending: Pending }
  | { readonly tag: "awaiting-profile-approval"; readonly client: SetupClient; readonly approvals: readonly ApprovalSummary[] }
  | { readonly tag: "applying-profile"; readonly client: SetupClient; readonly approvals: readonly ApprovalSummary[]; readonly pending: Pending }
  | { readonly tag: "choosing-credential"; readonly source: CredentialSummary }
  | { readonly tag: "previewing-credential-save"; readonly destination: CredentialDestination; readonly pending: Pending }
  | { readonly tag: "awaiting-credential-save-approval"; readonly preview: CredentialSavePreview }
  | { readonly tag: "saving-credential"; readonly preview: CredentialSavePreview; readonly pending: Pending }
  | { readonly tag: "confirming-key-check"; readonly source: CredentialSummary }
  | { readonly tag: "checking-key"; readonly pending: Pending }
  | { readonly tag: "finished" | "cancelled"; readonly reason?: "escape" | "interrupt" | "eof" | "signal" | "declined" }

type SetupModel = { readonly context: SetupContext; readonly step: SetupStep }
type UiAction =
  | { readonly type: "ClientToggled"; readonly client: SetupClient }
  | { readonly type: "ClientsConfirmed" | "Back" }
  | { readonly type: "Cancel"; readonly reason: "escape" | "interrupt" | "eof" | "signal" }
  | { readonly type: "ProfileApprovalAnswered"; readonly accepted: boolean }
  | { readonly type: "CredentialDestinationChosen"; readonly destination: CredentialDestination }
  | { readonly type: "CredentialSaveApprovalAnswered"; readonly accepted: boolean }
  | { readonly type: "KeyCheckConsentAnswered"; readonly accepted: boolean }

type SetupEvent =
  | { readonly source: "ui"; readonly revision: number; readonly action: UiAction }
  | { readonly source: "owner"; readonly revision: number; readonly commandId: number; readonly observation: SafeSetupObservation }

type SetupCommand =
  | (Pending & { readonly type: "PreviewSetup"; readonly client: SetupClient })
  | (Pending & { readonly type: "ApplySetup"; readonly client: SetupClient; readonly installDigest?: string; readonly rulesDigest?: string })
  | (Pending & { readonly type: "PreviewCredentialSave"; readonly destination: CredentialDestination })
  | (Pending & { readonly type: "CaptureAndSaveCredential"; readonly destination: CredentialDestination; readonly saveDigest: string })
  | (Pending & { readonly type: "RunConsentedKeyCheck" })

type Transition = { readonly model: SetupModel; readonly commands: readonly SetupCommand[] }
declare function transition(model: SetupModel, event: SetupEvent): Transition
declare function view(model: SetupModel): SetupScreen
declare function execute(command: SetupCommand): Effect.Effect<SafeSetupObservation, SetupCommandError>
```

`SetupContext` stays present while the `step` changes, so selected hosts, active host, and prior results survive credential and verification steps. The event union separates pure UI actions from owner observations. The reducer accepts an event only for the current `revision`; an owner observation must also match the current step's pending `commandId`. Going Back before a write increments the revision and invalidates the old preview, so a late answer or command result cannot advance the new screen. Back is disabled once an apply/save command starts; the current owner then reports complete, partial, or recovery state.

`ProfileApprovalAnswered(true)` emits `ApplySetup` using the install/rules digests already held in the current `awaiting-profile-approval` step; the UI event supplies no digest. Choosing a future credential destination emits `PreviewCredentialSave` only. After an owner supplies a sanitized change summary and proposal digest, `CredentialSaveApprovalAnswered(true)` may emit `CaptureAndSaveCredential` with that digest; the command must call the owning credential boundary and must not implement storage itself. The current version-one credential flow does not provide a destination-specific save proposal/digest contract, so this sequence is conditional on specification and an owner API decision. Key-entry ordering relative to that preview can remain open, but any entered string must exist only in the short-lived masked-input/credential adapter call; there is no secret-bearing model state or event. The existing optional check's count and timing policy remain with its current owner. Only safe, sanitized observations return to the UI model.

The candidate flow can retain the current per-host ordering:

```text
inspect client status
  -> select hosts (installed hosts checked by default)
  -> for each selected host, in order
       preview through that host's v1 owner
       -> unsupported/conflict: explain, keep result, continue or stop per accepted policy
       -> approval required: show that host's owned changes -> approve/decline
       -> approved: call the same owner with exact install/rules digest(s)
       -> record complete / partial / next actions -> continue to next host
  -> present one common credential choice only if its source/usage is truly common
  -> optional explicitly consented bounded key check
  -> offline readiness summary and next actions
```

Another viable design gathers every selected host's preview before asking each host's confirmation, allowing the user to review the full set together while preserving separate approvals. This is a plan-first variation, not a decision to replace today's per-host prompt sequence. A one-confirmation-for-all flow is a larger contract change and needs a clear policy for a conflict or write failure halfway through a multi-host apply.

## Synthesis and disconfirmation

**Convergent patterns.** Effect's `Prompt.Custom`, XState, Elm, `effect-machine`, and a local reducer all separate state from incoming events, and can represent transitions without relying on a terminal renderer. The new `effect-machine` evidence matters: unlike the v3 `@effect/experimental/Machine`, it declares an Effect 4-compatible peer and its own published source tree pins Effect 4.0.0/TypeScript 7.0.2, while documenting parent actors, back-navigation support, Effect tasks, and path simulation. That makes it the strongest dependency candidate to compare; those claims still need app-level execution. Effect `Prompt` and the v1 setup engines already separate leaf prompt execution and external work; Elm's command model remains a clear local-reducer shape. CLIG and GOV.UK guidance converge on explicit exits/TTY handling, clear choice labels, prior-answer preservation, visible review before commitment, focused questions, and actionable failures. These are useful patterns, not empirical Hapsland findings.

**Trade-offs.** A typed reducer makes state/event decisions inspectable with little coupling, but can become a hand-maintained state table whose result duplicates `SetupResult`. `effect-machine` supplies Effect-native actors, typed state/event schemas, task lifetimes, and transition simulation; it may eliminate hand-written dispatch and produce more useful state-path tests, but adds a young 0.x dependency and actor semantics beyond a short serial interaction. Its state, event, snapshot, task, and inspection features still need Hapsland's secret and digest policy, and task interruption cannot replace a v1 owner's journal. XState can model hierarchy, invocation, graph paths, and richer concurrent branches, but a separate runtime and Effect adapter add more concepts than `effect-machine`. Effect `Workflow` gives durable execution and resume semantics, but requires an engine and an operation-persistence contract that this foreground CLI does not need. Effect `Prompt` handles terminal question mechanics but is not full conversation state. The current Effect generator remains the least code for today's linear baseline; a typed session model is justified only for new branches that benefit from inspectable transitions.

**Recommendation.** Keep one transient session model with a shared context for selected hosts/results and a typed step for the currently visible question or engine gate. Separate pure UI events from sanitized v1 owner observations; commands/tasks call only existing owners. Preserve per-host proposal digests and results, reject stale UI and command replies with a revision plus command identity, and do not permit Back to imply a rollback after mutation begins. Keep secrets outside the model and events, and preserve unattended JSON/save-plan as a separate path. This interaction architecture is the primary finding; it does not select a library. Compare a small local reducer plus Effect commands against one `effect-machine@0.28.0` parent actor using the same transitions and tests before fixing implementation. If the branch set stays small and serial, keep the reducer or current Effect sequence; if the package passes exact-target testing and makes paths materially clearer at acceptable dependency cost, it can be promoted from `OPTIONAL INTEGRATION`. No production dependency or product contract is adopted here.

**Strongest case against an explicit model and against the local reducer.** Hapsland may only need a handful of sequential prompts; then a second state table restates `SetupResult` and review now requires matching two sources of truth. In the other direction, `effect-machine` may be the better implementation: its exact peer admits Effect 4, its development tree uses this project's exact Effect and TypeScript pins, and actor tasks/simulation could replace a hand-built dispatcher while making asynchronous outcomes easier to exercise. Choosing the local reducer before comparing it could recreate a small state-machine framework with fewer safeguards. The package's newness alone is not grounds to reject it. The costs to measure are actor/0.x API coupling, async interruption around write-owning owners, secret-safe observability, target Bun build behavior, and whether its extra features are needless for a serial CLI.

Evidence that should change the implementation choice includes a head-to-head prototype under Bun 1.3.14 and TypeScript 7.0.2 showing that `effect-machine@0.28.0` preserves exact v1 approval digests, safely rejects stale results after Back/Cancel, surfaces owner partial/recovery outcomes, contains no sentinel key in state/events/inspection, and reduces model/test complexity versus the reducer. A typecheck/build/test failure, unsafe or surprising interruption behavior, or no measurable clarity benefit favors the local reducer. If user research shows the journey remains linear, the current Effect sequence plus distinct cancel/empty outcomes may be enough. If cross-process human resumption becomes required, evaluate Workflow separately and specify its store, retention, secrecy, replay, and cancellation contract first. Documentation and peer ranges do not establish suitability.

## Limitations and primary-source index

This report inspected the current local sources and first-party documentation and package metadata. It did not install `effect-machine`, XState, or Robot3; did not run a compatibility or terminal test against Effect `4.0.0`, Bun `1.3.14`, `effect-machine`, XState, or Robot3; did not exercise a real or isolated Keychain/Secret Service; did not contact Jev; and did not conduct user research. The exact Effect `4.0.0` declarations were inspected only because the normal dependency is already present through this worktree's shared `node_modules` symlink. `npm view` was used only as a read-only registry metadata query for versions and licenses, not to install packages. No runtime, platform, accessibility, or design-acceptance claim follows.

General discovery was bounded to two rounds, followed by the narrow Effect-machine addendum documented above. This report does not establish that no smaller, newer, or domain-specific CLI workflow library exists. It did not compare hosted orchestration, event-sourcing frameworks, Redux-based application stores, or every statechart package. Those were omitted because the intended boundary is a single foreground local setup interaction and current setup owners already carry persistence and side effects. If those assumptions change, repeat candidate discovery rather than treating this short list as complete.
