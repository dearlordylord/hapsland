## Historical Claude feedback boundary

Claude's synchronous `PostToolUse` follows a successful native edit. It supplies a feedback point after the edit; a top-level `decision: "block"` asks the agent to repair current findings and cannot undo the edit or prove another model action. The exact tested event path is a successful, attributable, named-file `Edit` or `Write` under an authorized semantic root. Shell and external writes, interactive sessions, other Claude versions, and unproven multi-file behavior have no acceptance claim here. The early [Claude and OpenCode host probes](../evidence/host-94/claude-2.1.218-local-probe.json) established exact-binary event and scripted-provider delivery shapes, without real-model reaction.

In this earlier path, the built-in mode was `advisory`. Only the user configuration layer could enable `block-current-findings`; a project could narrow an opted-in user to advisory and could not grant blocking authority. An explicit user advisory choice denied project blocking. Missing, malformed, unreadable, or unauthorized mode state could not grant a block. The captured mode and current authority both had to permit blocking at the final handoff barrier. A later opt-in could not upgrade an already admitted advisory ticket, and revocation before handoff suppressed a block without repurposing its finding as another ticket's advice. A fresh tool use received its own admission and policy decision. An already started host write could not be recalled.

Only a nonempty, current, successfully evaluated rule finding is acting advice. Clear, skips, backend failures, and operational notices cannot become a block. A mixed response may include a separately labelled informational notice, while the repair request applies only to findings. The resident selects the final mode-specific envelope and enforces at most five combined items and 2,048 UTF-8 bytes for the complete serialized JSON line, including newline, before leasing. It selects whole findings in collection order and may append notices within the bound. Oversized findings remain pending or expire; a fitting notice may be sent as advisory. Clear and no work are quiet. The CLI writes the selected line without changing its content. The selected controlled host fixture showed a production block reason in the next scripted provider request, a quiet clear response, and a notice-only advisory response: [block](../evidence/host-94/validation/claude-production-block-20260924.json), [clear](../evidence/host-94/validation/claude-production-clear-20260924.json), [notice](../evidence/host-94/validation/claude-production-notice-20260924.json). This establishes envelope delivery in that scripted loop, not authenticated model reaction.

Claude's bounded synchronous path uses an opaque admission ticket bound to resident lifetime, canonical root, host/version, session, agent when supplied, and native tool-use ID. The ticket proves accepted ingress only. Collection checks the exact ticket, credential and admission generations, advicee, expiry, and current work. The final synchronous barrier rechecks those facts, ticket-local supersession, result freshness, and any lease immediately before response encoding. A later *different* tool-use ticket does not retroactively invalidate an earlier clear claim. A finding still requires current workspace revalidation. No ticket nonce, credential, raw source, host payload, or internal authority ID belongs in host output.

| Ticketed collection status | Meaning at the bounded Claude hook |
| --- | --- |
| `advice` | Current finding or operational notice is selected and leased; submit the bounded line and acknowledge after the writer callback. This takes priority over terminal status. |
| `pending` | Admission, a derived unit, validation, or deliverable output remains unfinished; poll within the existing hook budget. |
| `clear` | At least one eligible unit completed validated zero-finding review, all ticket units are successful clear, and no item or ticket-local supersession remains. This describes the admitted snapshot. |
| `delivered` | Every ticket unit succeeded, at least one finding was finalized, and no item remains. It never means clear. |
| `unavailable` | Backend, credential, capacity, stale, lost, or expired authority prevents a complete clear claim. A mixed success/failure ticket stays unavailable after its advice drains. |
| `no-work` | Accepted ingress closed with zero eligible units and no pending notice. A missing ticket cannot produce this status. |

The resident tracks every unit from admission through final retention or failure; an empty advice list or global `stats` is insufficient to prove clear. Ticket retention is bounded to 600,000 ms and 256 records; eviction, restart, failed acknowledgement, and lost authority cannot become clear. The compiled offline cold-clear fixture returned ticketed `clear` without a host submission after a prior polling failure had exposed the need for these terminal distinctions ([sanitized control](../evidence/host-94/validation/terminal-clear-cold-result.json)). The historical Claude CLI budget was 3,900 ms, bridge ceiling 4,400 ms, and native hook ceiling five seconds. These are tested implementation envelopes, not guarantees for live Jev latency. The current target contract specifies finish waiting and cancellation separately.

## Remaining decisions and evidence

The Claude preview decision concerned this exact controlled-backend, headless profile. It did not declare general Claude support or extend the pinned installed-release cells. A live Claude plus Jev pass was drafted but not executed. Such a pass needs a separate runner mode that cannot silently use the controlled backend, exact same-profile authentication, repository and destination consent, source-free attribution, bounded source and provider calls, and a clear distinction between application dispatch reservations and actual HTTP attempts. A late resident finding after hook closure is not host delivery. The selected earlier live Jev milestone had a 7,424 ms clear evaluation, which makes same-hook delivery uncertain under the historical five-second native ceiling; this one observation is not a latency distribution. OpenCode's exact-version scripted-provider probe showed `tool.execute.after` and output mutation reach the next local provider request, but authenticated model reaction, authority races, and restart remain unverified ([probe](../evidence/host-94/opencode-1.14.44-local-probe.json)).
