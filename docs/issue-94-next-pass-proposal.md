# Issue #94: proposed next host acceptance pass

**Decision requested:** approve the bounded follow-up below, or defer host support work. This is a proposal for review, not authorization to start sessions. Neither Claude Code nor OpenCode is declared supported.

## Evidence behind the proposal

The first [Claude Code 2.1.218 pass](issue-94-host-validation.md) used five authenticated headless sessions with an offline controlled Hapsland backend. The no-advice control passed. The finding fixture made one matched native edit and produced one context submission, but no later native repair; the retained evidence cannot classify that older submission as a rule finding rather than an operational notice. The stale fixture changed the file before review admission could be established. The timeout fixture kept the edit and returned without advice in 4.361 seconds. The unavailable-backend fixture kept the edit but produced one unclassified context submission. The five-session ceiling is exhausted. Restart and a true host failure were not exercised. OpenCode 1.14.44 has no saved provider credential and had no authenticated run. These are selected outcomes, not delivery rates.

The [#97 Codex measurements](issue-97-delivery.md) show why host submission, model reaction, and latency need separate evidence: a subsequent-hook path stranded a finding without a later edit; a bounded Stop collector produced same-turn repairs when results were ready, while late results timed out; native background output sometimes reached the model and sometimes lost its opportunity at headless teardown. Those results concern Codex 0.156.1 and do not establish Claude or OpenCode behavior. The five-second Stop bound was only a candidate, not a validated cross-host promise. For #94, measure each host's own hook launch, review completion, submission, later native edit, and session end rather than importing Codex timing assumptions.

## Finish offline before any new host call

1. **Verify the evidence reducer.** Feed synthetic Claude `assistant` tool-use JSON and OpenCode 1.14.44 tool-use part JSON through the actual stream parser and bridge. Include unknown shapes, duplicate events, mismatched call IDs, missing paths, model text without a tool call, a repair before submission, and an operational notice. Only a recognized rule-finding submission followed by a distinct matched model-originated native repair may set `modelReaction: observed`. Retain only booleans, counts, relative milliseconds, and exact host version/mode in run records. The current reducer's unit tests are a starting point, not an end-to-end bridge check.
2. **Classify the actual controlled handoff.** Use a fixed synthetic finding marker in offline fixtures and verify that the bridge marks `findingSubmitted` separately from `noticeSubmitted`; a generic nonempty `additionalContext` is insufficient. Verify the next scripted-provider request receives that marker in both hosts and that a clear or unavailable result cannot be counted as a finding. Keep this scripted check distinct from authenticated reaction evidence.
3. **Make the stale race deterministic.** Instrument the disposable resident or test bridge to emit a source-free `admitted` acknowledgment for the exact tool-call alias. Mutate the synthetic file only after admission and before the delayed decision completes. Offline tests must demonstrate that this ordering can be reached and that neither stale snapshot nor mismatched recipient is delivered. If the real-host ordering misses the window, classify the run `inconclusive`; the absence of a submission alone does not pass.
4. **Build a bounded restart fixture.** First session admits delayed work and ends; stop its disposable resident, start a second host session with a new recipient, and require no old finding in the second context. Prove source-free recipient aliases and resident lifetime transitions in an offline fixture. Treat a backend failure separately from a host crash; the first pass's `failure` scenario only injected backend unavailability.
5. **Harden the run gate.** Make the new runner persist a source-free pass ledger and refuse the next invocation when the per-host or total count is exhausted. Pin Claude to the cached executable that itself reports `2.1.218`; the PATH command now reports `2.1.281`. Pin OpenCode to `1.14.44`. Confirm the exact executable's login status read-only just before its pass. No credential files or host transcripts may be printed or retained.

Any production behavior gap found during these offline checks goes to the product owner for a separate fix and deterministic test before another host call. Do not change product code as part of acceptance evidence collection.

## Proposed bounded run, only after offline checks pass

Use one disposable Git repository and isolated Hapsland state per scenario, a normal authenticated host provider/model, and a controlled offline Hapsland backend. Run sequentially, away from #95 paired runs. Each session gets one synthetic initial native edit request, a 90-second host ceiling, and a 2 MB output ceiling. Claude Code has a five-second host-enforced native hook timeout. The OpenCode 1.14.44 adapter uses a 4.5-second plugin watchdog and bounded return path; this is an adapter bound, not a native OpenCode hook timeout. No Jev calls. Stop the entire host pass on a version/auth mismatch, raw-data retention, unbounded process, output ceiling, or edit failure. The staged cap is **eight sessions per host, sixteen total**; the ledger must enforce it across invocations.

| Stage | Sessions per host | Proceed condition |
| --- | ---: | --- |
| A: all-clear control and rule finding | 2 | Control has one native edit, zero submissions and no repair. Finding has a classified rule submission, matched native initial call, later matched model-originated repair after submission, and final repaired file. If either fails, stop that host; report submission and reaction separately. |
| B: stale, no-later-event/timeout, backend unavailable, host failure, and restart pair | Up to 6 | Run only after Stage A passes. Stale requires post-admission mutation and zero stale finding delivery. Timeout and unavailable remain bounded and preserve the edit, with notices counted separately. Host failure preserves the completed edit and reports whether the host or hook failed. Restart uses two sessions and proves no old recipient advice reaches the new one. A no-later-event result is `undelivered`, `submitted-unreacted`, or `observed-reaction`, never silently counted as clean. |

For each run, record host version, mode, platform, scenario, host outcome, initial native call matched, review admitted/completed outcome, classified finding/notice submission count, edit-to-submission interval (including host launch uncertainty), later matched repair, final synthetic state, and any ceiling hit. Record the timestamp source and measurement boundary. Do not equate a hook's elapsed time with native edit-to-agent-visible latency. A host-event timestamp after advice is a repair opportunity observation, not proof of when the model read the finding. Do not retain raw JSONL, prompts, source, credentials, model replies, or source-bearing Jev responses.

OpenCode may enter Stage A only after a read-only check reports a usable credential for the **same profile** used by `opencode run`, and its exact 1.14.44 binary and plugin-loading mode are verified. Current `opencode auth list` reports zero credentials. A missing login is a prerequisite failure, not an adapter failure; do not launch an OpenCode model session to discover it.
