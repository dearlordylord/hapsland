# Issue #94: optional Claude PostToolUse block for current findings

**Decision requested, 2026-09-24:** Authorize an **offline implementation** of an explicit opt-in Claude-only `PostToolUse` `decision: "block"` for a current, acting Noul rule finding after a successful direct edit, or defer that stronger behavior. The recommendation is to authorize the bounded offline implementation and tests below. This document is a proposed Hapsland product contract, not approval for another authenticated host session, a Jev call, or a Claude support declaration. The existing Claude advisory mode remains the default. Codex and OpenCode behavior stays as implemented; OpenCode host acceptance remains postponed.

## Evidence and limits

The approved two-session [repair-wording follow-up](issue-94-next-pass-proposal.md) is complete. Its authenticated Claude Code `2.1.218` control passed. In the finding arm, Hapsland submitted one classified `r6_bare_domain_value` finding through a successful hook, but no later model-originated native repair or matching successful repair hook was observed; [sanitized finding evidence](../evidence/host-94/validation/claude-repair-wording-finding.json) records the failed acceptance gate. The earlier authenticated Stage A finding also had no observed repair. These are two selected failures to observe repair, not a reaction rate or proof of why Claude did not repair.

The exact-binary [offline delivery fixture](issue-94-delivery-diagnosis.md) showed the production advisory finding and explicit repair request in the next scripted provider POST. A separate fixture-authored, source-free `{ "decision": "block", "reason": "..." }` reached that POST as a user message. That block arm did **not** run production Hapsland blocking output, an authenticated provider. It establishes envelope delivery in one controlled host loop, not model obedience.

Claude's [hooks reference](https://code.claude.com/docs/en/hooks#posttooluse-decision-control) documents `PostToolUse` after a successful tool call, with a top-level `decision: "block"` that adds `reason` beside the original tool result. The original edit has already happened; this decision does **not** roll it back, replace the tool output, guarantee another model turn, or guarantee a repair. The current documentation is mutable and is not a pinned `2.1.218` runtime contract. The acting-finding versus notice distinction is the selected Hapsland feedback rule.

## Proposed product contract

Offer a Claude feedback mode with `advisory` as the built-in default and `block-current-findings` as an explicit **user-owned** opt-in. Add a strictly decoded mode field to the existing built-in → user → project configuration system, retaining its origin in the captured policy. Only the user layer may enable `block-current-findings`; a project layer cannot enable or re-enable it. An explicit user `advisory` denies blocking even if a project requests it. A project may set `advisory` to restrict an opted-in user to advisory behavior for that repository. Omission inherits the lower layer. Invalid, unreadable, ambiguous, or unauthorized mode configuration resolves to no block authority and fails closed for the affected hook rather than silently upgrading to block. The mode is captured with the admitted observation and rechecked against current user/project authority at the resident's final handoff barrier: block requires both an opted-in captured mode and a still-authorized current mode. A changed or revoked opt-in before that barrier suppresses the block and releases its selection for a fresh, separately authorized collection; it must not be converted to an advisory reply from the stale lease. A later opt-in cannot upgrade a ticket admitted in advisory mode. The authority check shares the same barrier as finding freshness; revocation after host handoff begins cannot recall written bytes.

The setting applies only to Hapsland's synchronous Claude Code `2.1.218` direct `Edit|Write` `PostToolUse` path. The host event must represent a successful native edit with an attributable named file under the authorized semantic root and the same accepted Hapsland review path. The initial Noul-only rule pack and its configured probability threshold decide whether a finding is acting; the host envelope must not make a new model decision or promote a notice to a finding. An acting item is a nonempty rule finding from a successfully evaluated immutable input that is still current at handoff. An operational notice, skipped or unreviewed edit, and zero-finding evaluation are never acting.

For a leased response containing at least one current acting finding, emit **exactly one** top-level JSON object on stdout, exit zero, and use this shape:

```json
{"decision":"block","reason":"Hapsland found a current rule finding after this edit succeeded. Repair the listed finding(s) in the file, then continue.\n...bounded finding lines..."}
```

The `reason` uses Hapsland's existing bounded rule identity, declaration, probability, and message formatting for selected findings. It asks for repair without claiming that the edit was prevented or that a repair will occur. It must not include credentials, raw source, provider response text, ticket IDs, lease tokens, session IDs, or internal status. Do not add `hookSpecificOutput.additionalContext`, `updatedToolOutput`, `continue: false`, `systemMessage`, or an exit-code-2 blocking path to an acting response. If a response also contains a notice, place it in a separately labelled informational section of `reason`; the repair request applies only to findings. The presence of a notice alone must never produce `decision: "block"`.

Preserve the **five combined finding/notice items** and **2,048 UTF-8 bytes for the entire serialized host JSON line, including its newline**. The **resident** must select and construct the final mode-specific host envelope, calculate its exact serialized UTF-8 byte count, and enforce both bounds **before leasing** selected items. The existing advisory-size calculation cannot establish that a block response fits. The CLI receives the already selected, bounded envelope and only writes that exact line; it must not transform, re-budget, or decline a leased block after selection. Select whole current findings in existing collection order, then include notices if space remains; never include partial rule text. Leave additional eligible items pending for later bounded collection. If no acting finding fits a block envelope but a notice fits its advisory envelope, lease and emit that notice-only advisory response while the finding remains pending or expires under the existing policy. If neither fits, return quietly and retain or expire the items; never emit a truncated or misleading block. Clear and no-work are quiet.

### Authority and failure behavior

Use the existing Claude v2 admission ticket and original recipient: canonical root, host/version, session, and `tool_use_id`, with resident lifetime and credential/admission generations. A ticket identifies the exact accepted ingress, not a successful review. No different tool call, session, root, or replacement resident may collect its finding. Keep the ticket and lease token out of host output and retained evidence.

The resident must revalidate the complete retained evaluation and current work authority before selecting a block, then make a final synchronous handoff-barrier check of ticket ownership, ticket-local supersession, credential generation, captured and current mode authority, lease, expiry, and the exact current findings. The resident's response is the mode-aware envelope chosen under these checks, not raw findings for the CLI to reinterpret. There can be no awaited operation between this decision and response encoding. If the workspace changed, the review revision was superseded, revalidation fails, or authority is lost, suppress that block; do not turn a stale finding into a notice or `clear`. A later separate tool-use ticket does not retroactively invalidate a valid earlier handoff. A change after the handoff write begins cannot be recalled, so the contract makes no post-handoff freshness guarantee.

The writer must attempt the complete encoded line before acknowledging the lease; finalization remains coupled to the existing acknowledgement protocol. A disconnected writer, failed acknowledgement, expired lease, or uncompleted finalization must not mark a finding delivered or clear. A retry may redeliver a still-current item only through the same ticket's bounded lease rules. Delivery means attempted host handoff, not model visibility. Preserve the v2 terminal meanings: `pending` polls within the hook budget; `advice` selects the bounded output; `clear`, `delivered`, and `no-work` return quietly; `unavailable` does not become clear. A deliverable notice can accompany selected findings when the bound permits, and notice-only advice has priority over terminal statuses; it does not displace an acting finding that fits. A backend, credential, capacity, stale, lost, or expired outcome without a current finding must never block. A notice-only backend/credential failure may use the existing bounded advisory notice; timeout, unsupported event, rejected admission, resident failure, and hook deadline return quietly without fabricating a block. The existing 3,900 ms CLI deadline, 4,400 ms bridge ceiling, and five-second native hook ceiling remain unchanged.

This proposal does not add a `Stop` hook. A `PostToolUse` block has one chance at the completed edit's feedback point. It does not make a later turn or final-answer gate available, and Hapsland must not claim that it prevents a user from accepting an uncorrected result.

## Offline implementation and verification gate

Implementation is limited to the Claude output policy, its configuration and strict decoding, byte-aware resident selection, and the compiled CLI handoff. Keep the existing Effect `Decision` / `DecisionModel` review path and `@effect/ai-typesafe` provider; ordinary tests use the controlled offline backend. Do not change Codex v1 collection/output or OpenCode v1 behavior.

Deterministic tests must cover: built-in advisory default, user opt-in, explicit user advisory deny, project advisory restriction, project block without user authority, malformed or unreadable mode, opt-in revocation between admission and final handoff, and later opt-in that cannot upgrade an advisory ticket; one and several current acting findings; notice-only and mixed finding/notice responses; all-clear, no-work, pending, and each unavailable outcome; exact five-item and 2,048-byte boundaries using the resident's serialized block line **before lease**, with CLI byte-for-byte writer equivalence; oversized first item with a later fitting item; an oversized acting finding with a fitting notice that yields notice-only advisory output and leaves the finding pending; stale content and ticket-local supersession before the final handoff barrier; wrong recipient/lifetime/credential generation; simultaneous collectors, failed writer/acknowledgement, and lease expiry; deadline and backend/credential failure. Assert that no notice, stale, failed, or unreviewed outcome emits a block and that the host JSON carries no ticket, credential, or raw source.

After the deterministic suite and build pass, run **one offline scripted-provider fixture** through the compiled bridge, CLI, and resident with the exact cached Claude Code `2.1.218` binary. Require one successful native edit, one completed current controlled Noul finding, a valid production block envelope, and that envelope's bounded rule reference and repair request in the parsed next provider POST. Include a quiet clear control and a notice-only control. Retain only source-free booleans, counts, timing, byte totals, and status; remove raw provider requests, host JSONL, source, prompts, and hook payloads. The fixture proves delivery shape only, not an authenticated model reaction.

Any later authenticated host acceptance pass requires a separate, concrete approval with its own durable session ledger and bounds. It must distinguish one matched initial edit and successful hook, one classified production block submission, a subsequent distinct model-originated native repair and successful matching repair hook, and the final expected file. Stop on failed gates. The previous approved two-session allocation is exhausted; do not retry it. A Claude support declaration remains gated on real model reaction, stale and failure-path authority, and the remaining [host validation ledger](issue-94-host-validation.md). Neither offline delivery nor a host hook exit alone satisfies that gate.

## Owner decision

- **Authorize offline implementation (recommended):** accept the opt-in contract and verification gate above; review the resulting code and source-free evidence before deciding whether to authorize any authenticated session.
- **Defer:** retain today's advisory Claude behavior and the failed reaction gate; make no block-mode code change or support claim.

This is the product decision prompted by the two failed advisory finding observations. It does not reopen the completed two-session approval.
