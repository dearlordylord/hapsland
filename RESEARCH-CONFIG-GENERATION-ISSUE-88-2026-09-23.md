# Issue 88 implementation research: configuration documentation and JSON Schemas

**Status:** advisory implementation handoff, 2026-09-23. This note does not implement [issue #88](https://github.com/dearlordylord/jevs/issues/88). The user's single-wire-format decision is now recorded as the normative issue specification; this note supplies its research basis. It covers the pinned Effect 4.0.0-rc.116 API, the current configuration and rule-pack contracts, documentation ownership, generation mechanics, and validation. It does not supersede the Phase F specification or the repository consent and exclusion ADRs. The product has no users, so decoder acceptance of alternate prototype syntax was not a deployed compatibility obligation.

## Research brief and boundary

The question is how to make Effect Schema the structural source for a short README introduction, a complete configuration guide, and the two existing editor JSON Schemas while retaining accurate behavioral prose. The baseline is Effect's own JSON Schema projection plus a small product-owned generator; maintaining separate field tables or hand-written JSON Schemas fails the issue's single-source requirement. Representative workflows are a new user copying a small JSONC example, a user combining built-in/user/project layers, a rule-pack author using editor assistance, and a maintainer changing a field then running update/check. Source egress and remote Jev failure remain governed by existing repository consent and runtime code, not this generator.

This was a bounded pass over the issue, repository code/tests/docs, the pinned Effect API and a sibling generator. It is not an ecosystem survey. A validated counterexample showing that the pinned projection cannot express the now-specified wire schema would require a narrow schema-generation adaptation or a revised design before implementation.

## Architectural handoff

1. **Specified input contract after user decision.** [Issue #88](https://github.com/dearlordylord/jevs/issues/88) now specifies one Effect-defined configuration and rule-pack wire form, with explicit conversion to internal types. `ruleOverrides` is a map; rule packs use `schemaVersion`, `id`, `contentVersion`, `threshold`, `message`, and string-valued `criteria.false`/`criteria.true`. The array shorthand, alternate pack field names, object-form rule-pack criteria, and inert root `consent`/`enabled` fields are to be rejected. Repository enablement remains separate. The source-tree editor artifacts did not establish user adoption. Code-native structured Noul criteria in `src/questions.ts` are a different input surface: their intentional rendering to Effect Decision strings remains explicit in `src/jev-decision.ts`.
2. **Generate strict, complete JSON Schema documents.** Use RC.116's `onExcessProperty: "error"`; assemble Draft 2020-12 `$schema`, root metadata and `$defs` from the returned `Document`. The present hand-written artifacts use `const`, `oneOf` and named `$defs`; the projection may use `enum`, `anyOf` and inlined shapes. Assess accepted/rejected instance behavior, required keys, bounds, XOR pack references, unknown-key rejection and descriptions, not textual equality. A JSON Schema validator is an editor-contract check, not a substitute for JSONC parsing, glob validation, semantic pack checks or consent.
3. **Keep field descriptions in Effect annotations.** Annotate every root and nested field, including pack references and rule overrides. Traversing the projected schema, including `$ref`/`$defs` and possible `allOf` from key annotations, is a possible renderer design; direct Effect-schema introspection is another. Neither was tested here. The generator must avoid a second field catalog. Read true defaults from existing constants, and describe inheritance or explicit empty values without treating every optional field as having a default. The generator's short-version selection is explicit logic in the same module as full-version rendering.
4. **Keep behavioral prose authored.** Preserve the current guide's explanations for file discovery, JSONC, precedence, exclusion accumulation, repository enablement, credential selection, fixed Jev destination, pack path containment, rule applicability, and runtime failure behavior outside generated boundaries or in a single shared authored source if reused. This avoids treating structural Schema annotations as an authority on operational policy.
5. **Correct path-specific runtime claims before publishing generated prose.** The present guide's runtime-limit table and surrounding paragraphs describe configured per-file deadlines, retries, concurrency and event-wide advice budgets generally, whereas C6 shows the resident direct-event path uses fixed controls and the CLI's whole-file/JSON request path still reads configurable controls. State which settings are accepted/resolved and which path consumes them. Making ignored settings effective in the resident path is outside issue #88. The fractional threshold mismatch C4 needs a focused contract fix or a linked bug before fractional examples can be presented as accepted; the issue leaves that sequencing choice open.
6. **Use narrow generated boundaries and deterministic commands.** Mark the README introduction and the structural portion of the full guide. Preserve surrounding prose byte-for-byte, including custom examples if kept outside markers. Generate both JSON Schema files in the same update command. A check command should compute all prospective outputs, report every stale/missing target, return nonzero, and write nothing. Stable ordering/newlines and idempotent update should be observable. The only existing GitHub workflow is a macOS package conformance workflow scoped to an older branch; the implementation must decide the applicable regular validation gate instead of assuming a current CI job already runs the check.
7. **Respect the distribution boundary.** The README currently suggests copying schema files from a source checkout, while `package.json` does not include `docs/configuration.md` or `schemas/` in its publish file list. Issue #88 excludes release-distribution changes, so generated artifacts can be source-tree outputs here; any installed-package promise needs separate work.

The canonical-format cleanup is deliberately bounded. It removes prototype input spellings and redundant structural checks, while the conversion from validated wire values to runtime data remains a named step. Tests should assert that removed spellings are rejected, generated examples decode, malformed values retain useful field diagnostics, and repository consent cannot be supplied through configuration. No production behavior is changed by this research note.

## Verification and open decisions

The issue's agreed primary seam is the public update/check command in temporary fixtures: both documentation versions and both JSON Schemas are emitted; update is deterministic and idempotent; check succeeds when current and fails without writes for stale or missing artifacts; surrounding authored prose survives. Validate generated examples with `decodeConfigurationText`. Compare representative JSON Schema instances to the decoder for the chosen canonical nested fields, unions, optionality, bounds and unknown keys; if alternate forms are removed, test their rejection explicitly. Preserve known intentional differences such as JSONC syntax and semantic glob/path checks. Existing [configuration tests](./src/configuration/configuration.test.ts), [rule-pack tests](./src/rules/rules.test.ts), and [subprocess tests](./src/configuration/subprocess.test.ts) provide the focused regression seams.

Before implementation, select the exact validation command that will always run the stale-output check. A tiny executable projection plus validator fixture could check the specified boundary without building the generator. No paid Jev call or host session is needed. This report stops at repository source, one pinned upstream API, and one sibling prior-art implementation; editor integration and semantic equivalence of the generated artifacts remain untested.
